# ColoCrossing 洛杉矶候选数据库初始化

## 目标

- 将新购 ColoCrossing 洛杉矶物理服务器初始化为 Niffler 的候选 PostgreSQL 节点。
- 在不影响生产的前提下完成主机加固、存储与 RAID 核验、同版本 PostgreSQL 部署，以及两台应用服务器的真实 SQL 延迟测试。
- 用测试结果判断它是否适合替代当前生产主库。

## 当前事实

- 新服务器为 `E3-1240 v6 / 64 GB ECC / 2 x Samsung PM863a 1.92 TB / RAID 1 / 1 Gbps`。
- 服务器位于洛杉矶；`hd0526` 到该服务器的网络 RTT 约为 `0.78 ms`，OVH Hillsboro 到该服务器约为 `69 ms`。
- 当前生产主库已经迁移至 `rn-hybrid`，不是 `rn01`。未来若执行数据库迁移，数据源应为 `rn-hybrid`。
- 当前生产 PostgreSQL 为 15.18，应用通过 WireGuard 和 PgBouncer 访问。

## 非目标

- 本阶段不复制或迁移生产数据。
- 不修改 `hd0526`、OVH 的生产数据库连接。
- 不停止 `rn-hybrid`、`rn01` 或任何生产容器。
- 不修改 Cloudflare、DNS、Caddy 或公网流量入口。
- 不将 PostgreSQL 直接暴露到公网。

## 本阶段行为变化

1. 为新服务器配置独立 SSH 密钥和非 root 管理账号，确认密钥登录后关闭 root 密码登录。
2. 启用主机防火墙、登录防护、自动安全更新和时间同步。
3. 核验 RAID 逻辑盘、控制器缓存和电池状态；未确认写缓存保护前，不承载唯一生产主库。
4. 部署与生产兼容的 PostgreSQL 15.18 候选实例，先只提供测试数据库。
5. 通过受限私网连接，从 `hd0526` 和 OVH 分别执行连接建立、短查询和持续连接测试。

## 影响范围

- 新服务器会安装必要的软件并调整 SSH 和防火墙配置。
- 若为真实 SQL 延迟测试接入现有 `wg-db`，只新增一个候选节点和最小路由；不得改变已有 peer、PgBouncer 或生产数据库路由。
- 生产应用、生产数据库和用户流量在本阶段保持不变。

## 验证方式

- 新 SSH 密钥和非 root 管理账号可以登录，密码登录和 root 远程登录已关闭。
- 防火墙只允许必需端口，PostgreSQL 公网地址无法连接。
- 两块 SSD 健康，RAID 1 状态正常，控制器缓存与 BBU/CacheVault 状态有明确结果。
- PostgreSQL 版本、数据目录、TLS、角色权限、备份测试和重启恢复均通过。
- 两台应用服务器分别完成至少 30 次真实 SQL 延迟采样，记录平均值、P95、最大值和丢包情况。

## 回退与停止条件

- SSH 加固前必须保留当前会话，并先验证新密钥登录；验证失败则不关闭旧登录方式。
- 防火墙应用前保存规则并保持可回退入口；任何管理连接异常立即恢复。
- RAID 降级、磁盘介质错误、控制器缓存无保护、系统异常重启或 SQL 测试不稳定时，停止后续迁移评估。
- 生产迁移必须另开维护窗口并再次获得明确授权，本记录不构成迁移授权。

## 第一阶段实施结果

### 主机与访问控制

- 管理入口改为非 root 账号和独立 ED25519 密钥；root、密码和键盘交互登录已关闭。
- nftables 使用默认拒绝策略。PostgreSQL 只允许 `wg-db` 中的 hd0526（`.3`）和 OVH（`.4`）访问，公网 `192.3.170.102:55432` 实测无法建立连接。
- Docker、nftables、Fail2ban、unattended-upgrades、`wg-quick@wg-db` 和候选 PostgreSQL 服务均已启用自启动并处于 active。

### 候选数据库

- 使用与生产一致的 PostgreSQL 15.18 镜像，地址为 `10.72.0.5:55432`，只承载隔离的 `benchmark` 测试库。
- 数据目录启用 checksums；`fsync`、`synchronous_commit`、`full_page_writes` 和 TLS 均开启。
- 服务重启后容器恢复 healthy，100 万条测试数据完整；两台应用节点均以 TLS 1.3 成功查询。
- 已对测试库执行 `pg_dump`、`pg_restore` 和独立恢复库校验，恢复后的 100 万条数据完整；临时恢复库与备份文件已删除。
- 仓库配置与服务器落盘文件校验和一致；SSH、防火墙、Fail2ban、Compose 和候选库健康检查均通过。

### 延迟结果

| 测试节点 | WireGuard RTT 平均 | 持久连接 SQL 平均 | P95 | 最大值 | 失败事务 |
|---|---:|---:|---:|---:|---:|
| hd0526 洛杉矶 | 1.831 ms | 1.811 ms | 2.397 ms | 7.935 ms | 0 |
| OVH Hillsboro | 69.704 ms | 70.095 ms | 70.361 ms | 74.700 ms | 0 |

额外执行了 50 次“启动 psql、建立 TLS、查询、断开”的完整采样：hd0526 平均 `76.965 ms`、P95 `87.269 ms`；OVH 平均 `628.355 ms`、P95 `636.715 ms`。这组数据不代表连接池中的正常查询耗时，而是说明应用必须继续通过 PgBouncer 或自身连接池复用数据库连接。

### 测试链路回退

- hd0526 和 OVH 的原 `wg-db` 配置均备份为 `/root/wg-db.conf.pre-colocrossing-20260819T102252Z`。
- 如需撤销候选链路，只删除两台应用节点上指向 `10.72.0.5/32` 的新增 peer 并恢复对应备份；不得修改指向生产 `.1` 的现有 peer。
- 候选 PostgreSQL 可由 `niffler-postgres-candidate.service` 独立停止，不影响当前 `rn-hybrid` 主库或生产 PgBouncer。

## 迁移判断

- 从网络和基础数据库表现看，该服务器适合作为 hd0526 的后续主数据库节点；OVH 到它的 70 ms RTT 决定了 OVH 更适合作为故障切换应用节点。
- 当前仍不允许迁移生产：实际 RAID 控制器为 `LSI 9260-8i`，与订单中的 `9271-8i` 不一致；尚未取得虚拟盘 Optimal、写缓存策略、BBU/CacheVault 状态和 IPMI 凭据。
- 当前生产主库仍是 `rn-hybrid`，两台 Frontdoor 仍连接 `10.72.0.1:6432`。复制、停写、校验和切换必须在后续维护窗口中单独执行并再次获得授权。
- 收尾时主站、API、`us1`、`us2` 均返回 HTTP 200，说明本阶段没有影响现有公网服务。
