# 请求扣费记录金额类型热修复

## 目标

修复 PostgreSQL 环境下，付费请求保存请求级扣费决定后返回 500 的问题。

## 非目标

- 不改变钱包、套餐和混合扣费规则。
- 不修改现有金额数据。
- 不在本次热修复中重构全系统金额表示方式。

## 行为变化

- PostgreSQL 返回请求开始时的钱包余额时，先转换为应用当前使用的浮点类型。
- 写入时由 PostgreSQL 按 `numeric(20,8)` 规范金额，并用数据库按相同规则规范后的
  输入值校验返回记录，避免应用浮点舍入差异造成误判。
- 正常请求继续使用原有扣费决定；本次改动不放宽任何资金检查。

## 影响范围

- 仅影响 PostgreSQL 请求级扣费决定的保存后读取和按请求读取。
- 不需要数据库迁移，不修改钱包余额、套餐额度或历史账单。
- MySQL、SQLite 和内存实现保持原有存储类型与行为。

## 验证方式

- 单元测试覆盖小数超过 8 位、负余额和 `None` 的比较。
- PostgreSQL 查询测试确认两条读取路径都显式转换金额类型。
- PostgreSQL 集成测试覆盖保存扣费决定、重新查询并继续结算的完整路径。
- 持续集成使用真实 PostgreSQL 固定运行上述金额保存和读取测试，不能因未配置数据库而跳过。
- 发布后使用测试账号分别发送钱包请求和套餐请求，并确认日志不再出现
  `wallet_balance_at_admission` 类型不匹配。

首次运行新增 PostgreSQL 测试时，测试记录引用了未创建的供应商端点，数据库按外键
规则拒绝写入。测试数据随后缩减为本次修复所需的最小字段，避免无关供应商数据影响
金额类型验证。

数据模块全量 532 项测试中，531 项通过；现有
`provider_usage_projection_repair_records_delayed_retry_after_failure` 测试因插入供应商密钥时
漏填数据库已有的 `total_tokens` 必填字段而失败。该测试单独重跑仍以相同原因失败，涉及
供应商用量迁移，不涉及本次请求扣费记录金额修复，因此未在本次热修复中修改。
