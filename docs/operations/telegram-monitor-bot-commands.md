# Telegram 监控 Bot 命令设计

## 目标

让非运维人员也能从通知中看懂故障位置、实际影响和处理建议，并允许授权管理员在
Telegram 中查询三台生产服务器的状态和调整监控阈值。

## 非目标

- 不通过 Bot 重启服务、清理磁盘、执行 SQL 或运行任意系统命令。
- 不把 Telegram Token、Chat ID、数据库凭据或服务器 root 密钥发到消息中。
- 不提供多人权限管理；当前只允许已经绑定的私人 Chat ID。

## 行为变化

- `/` 改称“系统盘”，容器名改成对应的业务服务名称。
- 测试消息、真实告警、恢复消息和备份结果使用不同标题。
- `/status` 直接使用每台服务器的状态快照标题，不额外重复添加服务器标题。
- 日常备份成功消息只显示备份大小、存储位置和校验结果；详细编号、SHA-256 和对象
  路径继续保留在服务器状态文件和日志中。
- `rn01` 每 10 秒读取一次 Bot 更新，使用持久化偏移量避免重复处理消息。
- 设置命令支持同时修改三台服务器或只修改指定服务器。

## 安全边界

- 命令接收器只部署在 `rn01`，避免多台服务器同时读取同一条 Telegram 更新。
- 每条命令都核对 Chat ID、命令名、参数数量、整数范围和阈值先后关系。
- `rn01` 到 `hd0526` 使用独立的受限 SSH 用户和密钥。
- `hd0526` 的 authorized_keys 使用强制命令，并关闭终端、端口转发、代理转发和
  X11 转发。
- 设置文件采用临时文件加原子替换，拒绝符号链接，避免写入一半的配置。

## 影响范围

- 只修改监控脚本、备份通知脚本及其 systemd 单元。
- 不修改 Niffler 应用、数据库、Redis、Caddy 或 Cloudflare 配置。
- 设置更新在下一次监控执行时读取，不需要重启业务服务。

## 验证方式

- 本地脚本测试覆盖人性化文案、告警去重、恢复、参数范围和阈值关系。
- 三台服务器执行 Bash 语法检查及 systemd 单元检查。
- 使用授权聊天验证查询和设置命令；使用非法参数确认不会修改配置。
- 检查受限 SSH 密钥不能执行额外命令。
- 部署后复查前台、后台、PostgreSQL、Redis 和公开健康接口。
