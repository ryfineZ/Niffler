# Niffler 二开能力目录与处置建议

## 阅读说明

本目录按最终生效能力分类，不按提交数量或文件数量判断价值。完整提交和路径证据分别见：

- `generated/niffler_commit_catalog.tsv`
- `generated/niffler_path_commit_map.tsv`
- `generated/niffler_cluster_paths.tsv`

下表中的处置是审计当前阶段的建议；涉及数据删除、业务开关和生产拓扑的项目在实施前仍需按迁移门禁验证。

## 总览

| 能力域 | Niffler 最终能力 | 当前建议 | 核心理由 |
|---|---|---|---|
| 品牌与产品身份 | Niffler 名称、仓库、镜像、公开站点和文案 | `KEEP_REBASE` | 品牌必须保留，底层通用代码不应长期携带无关全局替换 |
| 商业化计费 | 分组售价、周期套餐、套餐供应商、钱包、支付、返利和账单展示 | `KEEP_REBASE` | Niffler 核心业务；需承接上游新数据/性能架构，不能恢复为上游默认业务 |
| 计费透支根修复 | 请求级资金准入、最终原子结算、负余额、欠款随套餐订单结清 | `KEEP` | 当前正确性基线；明确替代真实金额预占 |
| Niffler Core 新模型 | 产品策略、上游服务/账号、账号模型能力、灰度权威读源 | `KEEP_REBASE` | 已真实参与权限、售价和账号过滤；需要适配上游热路径架构 |
| Niffler Core 迁移工具 | readiness、旧接口投影、稳定观察、回滚证据、一致性看板 | `KEEP_REBASE` 后逐步收缩 | 迁移未结束前有价值，完成后不应长期占一级导航和热路径 |
| 旧真实预占 | 请求前写 `niffler_billing_reservations` 冻结可用余额 | `REMOVE` | 最终代码已强制关闭；与 8 月计费基线冲突 |
| 预占历史数据 | 预占表、事件、过期扫描、只读对账 | `KEEP_REBASE` | 用于收尾历史 active 数据；不能删除已执行迁移 |
| 错误返回规则 | 灰度改写平台/上游错误，记录风险命中 | `KEEP_REBASE` | 产品能力有效；规则读取应缓存并限制原始错误暴露 |
| 风险保护动作 | 配置暂停调度/禁用账号 | `REMOVE`（暂时） | 当前只有事件记录，没有执行器，界面语义误导 |
| 返利账本 | 灰度订单由新账本幂等发放，旧明细保留兼容 | `KEEP_REBASE` | 已是实际资金路径，必须保留双发保护和重试审计 |
| Provider/账号池管理 | 批量删除、筛选删除、批量冷却、测试、额度重置、统一状态 | `KEEP_REBASE` | 运营刚需；需叠加上游新调度、缓存和 OAuth 管理 |
| 导入兼容 | CPA、sub2api、嵌套 ChatGPT 授权、覆盖已有账号 | `KEEP_REBASE` | 迁移/运营刚需；需保留安全边界并迁入上游新凭证结构 |
| CCSwitch 兼容 | 余额查询、模型目录、导入辅助 | `KEEP` | 客户端兼容能力，冲突面较小 |
| Codex/Responses/图片 | 输入兼容、加密上下文、生图工具、原生图片事件、图片直通 | `KEEP_REBASE` | 产品已依赖；上游同域更新密集，只能做语义合并 |
| Grok OAuth | 订阅账号、PKCE、配额与 reasoning 记录 | `KEEP_REBASE` | Niffler 独有供应能力；迁入上游新 OAuth/Provider 架构 |
| 流式自动换号 | Responses 输出前容量错误自动换账号，记录预读首字 | `KEEP_REBASE` | 有业务价值；必须与上游端到端计时和失败边界统一 |
| 用量与统计 | 错误明细、官方应扣、Key 分组筛选、分页、时区和大对象存储 | `KEEP_REBASE` | 业务和运营依赖；金额只能读最终结算事实 |
| 邮件与注册 | 异步邮件队列、测试发送、投递历史、验证与密码重置 | `KEEP_REBASE` | 用户系统能力；需吸收上游后台任务保护 |
| 内容审查 | 上游账号级前置审查、费用与记录 | `DECISION_REQUIRED` | 有安全/合规价值，但会增加成本、时延并改变用户请求 |
| 受管理提示词 | 按用户分组注入提示和记录执行元数据 | `KEEP_REBASE` | 明确产品能力；必须保持协议角色语义和可审计性 |
| 公开站点与图片工具 | 多语言首页、模型目录、生图工作台、Infinite Canvas | `KEEP` | Niffler 产品前台，不应被上游管理端更新覆盖 |
| 后台体验 | 表格、移动端、钱包/套餐/用户/号池操作体验 | `KEEP_REBASE` | 用户可见价值高，需在上游新版页面上逐页重放 |
| CI/CD 与生产保护 | 固定产物、祖先校验、测试晋级、生产发布保护 | `KEEP` | 直接对应 Niffler 生产流程和误发布风险 |
| 监控与备份 | Telegram 监控、双节点拓扑、Postgres 备份和告警 | `KEEP` | 生产专属；与应用上游合并应解耦维护 |
| 临时迁移脚本 | sub2api 同步、Niffler Core 校验、一次性验证工具 | `KEEP_REBASE` 后归档 | 有审计价值，但不应与长期运行代码混在默认入口 |

## 1. 商业化计费与钱包

### 最终权威规则

- 钱包按量售价由产品策略或旧分组销售倍率决定；套餐额度使用自己的消耗倍率和供应商范围。
- 2026-08-10 后，请求调用上游前持久化 `billing_request_admissions`，最终结算必须读取这份请求级决定；缺失决定、供应商越界或重复结算不能猜测扣款。
- 有限钱包只有真实余额大于 0 才能作为按量支付来源；有效套餐仍可在钱包欠费时继续使用。
- 套餐只扣到 0，合法请求的超出部分继续扣钱包，钱包可因最后一批并发请求变负。
- 套餐直接选择供应商，可用模型随供应商当前模型关系动态变化；旧静态模型范围只作为待迁移兼容。
- 欠费用户购买套餐时，订单保存“套餐价格 + 下单时欠款”，到账事务先偿还订单记录的欠款再发放套餐。

### 必须保留

- 请求级资金准入、请求候选与准入同事务、最终结算幂等、结算失败重试。
- 周期额度、额度消耗倍率快照、套餐供应商快照、同一用户单一生效套餐约束。
- 分组/产品策略销售倍率、Provider 成本倍率、最终价格快照和用户消费/平台成本分栏。
- DoDoPay、支付订单统一展示、套餐发放/取消、人工迁移时间和额度覆盖。
- 钱包真实负余额显示、套餐和钱包分别展示、侧边栏摘要。

### 应剔除或还原

- 真实金额预占准入及其可配置开关。最终代码已将开关硬关闭，应进一步移除可误操作的管理编辑入口。
- 用过期缓存决定钱包或套餐最终放行。资金准入必须读取已提交数据库状态。
- 统计页面按当前价格、成功状态或旧字段重新计算历史金额；应统一读取结算事实。
- 旧 `allow_wallet_overage` 作为是否补扣钱包的业务开关；最终规则已统一为套餐不足部分补扣钱包。
- 已被供应商动态模型取代的套餐静态模型编辑入口；旧数据仅保留兼容和迁移标记。

### 合并上游时的保护线

- 不接受上游改动重新引入“估算不足即拒绝”或“缺少最大输出 Token 即放行/拒绝”的金额预占语义。
- 不直接覆盖 Niffler 的钱包、套餐、支付和最终结算仓储；先把上游数据层/热路径基础设施移植到 Niffler 的业务契约下。
- 任何调度架构变更都必须继续保存并校验请求级资金决定中的允许供应商集合。

## 2. Niffler Core

### 保留为业务权威

- 开启 `enable_new_routing` 的 Key/产品策略使用 `niffler_product_plans`、模型覆盖倍率、上游服务、上游账号和账号模型能力决定权限与调度范围。
- 错误返回规则真实改写灰度用户的错误响应。
- 返利账本在灰度范围内真实发放资金，并与旧返利明细保持兼容状态。

### 保留为迁移证据

- 路由尝试和结算快照是失败不影响请求的旁路记录。
- readiness、旧依赖稽核、旧接口只读投影、稳定观察、回滚演练证据和一致性看板用于迁移门禁。
- 已执行的数据库迁移、历史预占和事件记录必须保留；下线使用追加迁移和归档策略，不删除旧迁移文件。

### 应收缩

- 真实预占已停用；管理端不应继续显示可启用开关。
- 风险规则中的暂停调度/禁用账号没有执行器，暂时只允许 `record_only`。
- 迁移控制台和就绪页在迁移完成后移入高级运维入口；稳定期结束后停止新增无用影子记录。
- 新路由目前仍依赖旧 Provider catalog 作为传输快照，不能宣称旧模型已经完全下线。

## 3. Provider、OAuth、客户端兼容和模型目录

### 保留

- CPA、sub2api、嵌套 ChatGPT 授权文件导入，以及覆盖已有账号时保留分组/权限的规则。
- OAuth 客户端凭据外部配置；移除代码内置 Google 客户端凭据属于安全修复。
- CCSwitch 的余额、模型目录和配置导入兼容。
- Provider 模型导入、自动同步模型清单标记、账号测试和 Codex 配额重置。
- 账号统一调度状态、普通 5xx 不直接冷却账号、Claude Code 特定错误不扩大到 Provider 级冷却。
- Grok OAuth 订阅账号支持。

### 需要重做的部分

- 所有导入解析器迁入上游最新 OAuth/凭证契约，先把外部格式转换成稳定中间结构，再写 Niffler 上游账号。
- 账号测试、配额刷新和模型同步使用上游最新后台任务治理，避免维护任务压垮数据库或 Redis。
- 批量删除和“删除全部筛选”必须继续做占用检查、分页和明确审计，不能在上游新分页接口上退化为前端全量循环。

## 4. Codex、Responses、图片与流式执行

### 保留

- Responses 字符串输入和 Lite 请求兼容、加密上下文保护、reasoning ID 规范化。
- Codex 模型目录客户端版本、真实配额窗口、GPT-5.6 模型配置。
- 原生托管生图事件、图片结果续传、图片接口直通和生图费用修正。
- 输出前容量错误自动换账号和预读首字记录。

### 必须与上游语义合并

- 上游在 OpenAI/Codex/Responses、流式终态、SSE 控制、断连清理和端到端计时上的更新密集。不能把 Niffler 36 个相关提交原样重放到上游最终文件。
- Niffler 的“首字”目前记录成功尝试的预读时间；上游新增端到端首字和端到端总耗时，应同时保存“本次成功尝试耗时”和“用户从请求开始等待的耗时”。
- 输出前换号只允许在任何用户可见字节尚未提交时发生；一旦提交响应头/正文，不得跨账号重新开始并拼接两次响应。

## 5. 用量、统计与可观测性

### 保留

- 未登录请求不污染用量、平台本地拦截也有可解释记录、成功/失败/待结算状态修正。
- 官方应扣、Key 分组筛选、时间范围、分页总数、Provider 结算投影一致性。
- 大请求正文转外部对象存储、用量窗口与 Codex 配额窗口的真实口径。
- 用户和管理员分别展示用户消费、套餐扣除、钱包扣除、平台成本和毛利。

### 调整

- 首字与总耗时改成上游端到端口径，同时保留单次成功尝试字段用于诊断。
- 上游请求时间线、诊断和 worker 指标可替代 Niffler 部分自建状态展示；字段映射后再删除重复接口。
- 日统计补跑和 Provider 窗口聚合继续限压，叠加上游数据库压力保护。

## 6. 用户、邮件、内容审查和受管理提示词

### 邮件与注册：`KEEP_REBASE`

- 异步发送、失败状态、测试发送和历史记录应保留；注册验证和密码重置不能回退为同步 SMTP 请求。
- 合并上游 worker 治理、任务记录清理和数据库压力保护。

### 内容审查：`DECISION_REQUIRED`

- 当前能力会在进入目标账号前调用审查上游，记录命中和费用，并可能影响账号保护。
- 保留前必须确认适用用户/模型、失败时放行还是拒绝、审查费用由谁承担、正文留存和隐私规则。
- 未确认前不扩大范围；如果生产没有使用，优先保持关闭并保留配置/数据，不在上游合并第一阶段迁移运行时。

### 受管理提示词：`KEEP_REBASE`

- 按用户分组配置、执行元数据和审计记录有明确产品价值。
- 协议适配必须按 OpenAI developer、Anthropic system、Gemini system instruction 的原生语义实现，不能全都转换为同一种消息角色。

## 7. 前台、后台和品牌

- Niffler 品牌、多语言公共首页、模型目录、生图工作台和 Infinite Canvas 属于产品层，整体保留。
- 上游新版后台页面只作为底层能力和交互改进来源；Niffler 的支付、套餐、账号池、内容审查、Niffler Core 页面需在新版组件上逐页重放。
- 旧迁移控制台不应与“上游接入”“产品策略”混成一个日常页面；产品配置保留，迁移工具移入高级运维。
- 后台表格的服务端分页、筛选、批量操作、移动端和权限收紧保留；吸收上游同类更新时以 API 查询语义为准，避免前端全量取数。

## 8. 发布、生产监控和一次性工具

- 固定 CI 产物、提交祖先校验、生产受保护发布、测试环境晋级、外部 PostgreSQL 迁移预检必须保留。
- Telegram 监控、OVH/RN01 拓扑、Postgres 备份与告警是 Niffler 生产专属，应用上游合并不得覆盖其服务文件和环境模板。
- sub2api 同步、Niffler Core readiness、图片桥接验证等一次性脚本继续保留到迁移完成；之后移入 `scripts/oneoff/archive` 或单独运维仓库，并标明最后验证版本。
- 仓库根部的历史 `task_plan.md`、`findings.md`、`progress.md` 是过程文档，不是运行能力；最终审计完成后应归档，避免与后续任务文件冲突。
