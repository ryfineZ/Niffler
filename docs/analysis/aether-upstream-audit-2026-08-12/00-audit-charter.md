# Niffler 与 Aether 全量分叉审计章程

## 目标

以 Niffler 与 Aether 的真实共同祖先为起点，完整识别两条分支此后的代码、数据、配置、部署和产品行为变化，回答以下问题：

1. Niffler 二开了什么，以及每项二开的目的、现状和依赖。
2. Aether 上游更新了什么，以及每项更新解决的问题和引入的约束。
3. Niffler 二开项应保留、重做、删除还是还原到上游实现。
4. Aether 上游项应直接吸收、按语义重做、暂缓还是明确不引入。
5. 如何在不破坏 Niffler 现有业务、生产数据和发布流程的前提下分阶段迁移。

## 非目标

- 本审计阶段不合并上游、不修改业务代码、不执行数据库迁移、不部署生产。
- 不根据提交标题直接判断可合并性；标题只用于初筛，最终结论必须回到代码、迁移、配置、测试或运行证据。
- 不把 Niffler 当前实现简单视为“落后”，也不把 Aether 上游实现简单视为“更好”。每项按 Niffler 的实际产品目标重新评估。

## 比较对象

- 共同祖先：`ed75ae6d56ab03eb5e6e3cd87f2137880c99694d`，时间为 2026-05-20 01:06:58 +0800。
- Niffler 已发布主线：`origin/main`，审计启动时为 `908443291`。
- Aether 上游主线：`upstream/main`，审计启动时为 `654c4f697`。
- 本地未合并内容：当前分支、其他本地分支和工作区改动单独列入附录，不混入“已发布 Niffler 主线”的判断。

选择 `origin/main` 作为 Niffler 主比较对象，是为了获得稳定、可复现且不受当前脏工作区影响的结果。当前分支和未提交改动仍会单独审计，以免漏掉已完成但尚未进入主线的二开。

## 完整性口径

“每一处区别”分为两层：

1. 机器清单层：记录共同祖先到两条主线的每个独有提交、每个变更路径、增删行、路径状态、双方是否同时修改，以及两条主线最终文件是否相同。
2. 人工语义层：按子系统解释变更目标、主要入口、数据和配置语义、运行风险、测试覆盖、Niffler 与上游的重叠关系及处置建议。

机器清单保证没有路径被遗漏；人工报告保证不是只列文件名而没有行为判断。

## 子系统分类

- 流式执行、首字、超时、重试、换号与响应提交边界
- 调度、账号池、路由、缓存、准入与并发
- OpenAI、Codex、Claude、Gemini、Grok、Kiro、Windsurf、Antigravity 等协议和服务适配
- Redis、PostgreSQL、MySQL、SQLite、迁移、后台任务与用量持久化
- 计费、钱包、套餐、价格、配额、结算与支付
- 鉴权、OAuth、权限、安全、隐私和审计
- 管理后台、用户端、国际化、用量详情和监控界面
- 安装、升级、备份、隧道、反向代理、CI/CD 和生产运维
- Niffler 品牌、业务规则、生产拓扑及只属于 Niffler 的产品能力
- 架构拆分、依赖升级、测试基础设施和开发工具

## 处置标签

### Niffler 二开项

- `KEEP`：产品必要且实现健康，继续保留。
- `KEEP_REBASE`：产品必要，但底层应迁到上游新架构后重做。
- `REPLACE_UPSTREAM`：需求仍需要，但上游实现更完整，应由上游实现替换。
- `REMOVE`：已经过时、重复、危险或增加维护负担，应删除。
- `RESTORE_UPSTREAM`：二开改变了通用语义且没有 Niffler 特有价值，应恢复上游行为。
- `DECISION_REQUIRED`：需要业务负责人明确规则后才能决定。
- `SPLIT`：同一提交混合了应保留和应删除的行为，禁止整提交重放，必须拆分。
- `HISTORY_ONLY`：只保留为历史索引或证据，不进入实现清单。

### Aether 上游项

- `ABSORB_DIRECT`：依赖少、冲突小，可直接移植提交或小提交组。
- `ABSORB_SEMANTIC`：价值高，但因架构分叉只能按行为重新实现。
- `ABSORB_AFTER_FOUNDATION`：依赖上游基础设施，须先完成前置迁移。
- `DEFER`：有价值但当前收益不足以覆盖风险。
- `REJECT`：与 Niffler 产品、架构或运维边界冲突，明确不引入。
- `ALREADY_EQUIVALENT`：Niffler 已有等价或更完整实现，只需补测试或对齐边界。
- `SPLIT`：同一上游提交只有部分行为适合吸收，必须按行为拆分。
- `HISTORY_ONLY`：合并提交等只作历史索引，不作为可移植补丁。

## 证据等级

- `A`：代码、迁移、测试和运行事实相互印证。
- `B`：代码与测试或配置相互印证，尚无生产运行验证。
- `C`：根据代码结构和提交历史得出的高置信度判断，需在迁移前补验证。
- `D`：仅根据标题、文档或局部代码推断，不进入最终实施清单，必须继续核查。

## 多轮复核

1. 覆盖率复核：机器清单中的所有路径和独有提交必须有分类；抽查重命名、删除和双方同时修改的路径。
2. 技术复核：逐项挑战“保留、删除、吸收”判断，核对依赖、数据语义、接口兼容和测试证据。
3. 实施风险复核：核对迁移顺序、数据库版本、生产配置、性能、回退方式和发布链。
4. 最终一致性复核：报告、决策矩阵、路线图和机器清单中的数量与标签必须一致。

## 输出物

- 审计方法与基线说明
- 双向逐提交清单
- 双向逐路径清单与冲突热点清单
- Niffler 二开目录及处置建议
- Aether 更新目录及吸收建议
- 子系统详细比较报告
- 分阶段迁移路线图、验证矩阵和回退边界
- 多轮复核记录与未决事项

## 验证方式

- 使用固定提交号重新生成清单时结果一致。
- 清单数量与 `git rev-list`、`git diff --name-status`、`git diff --numstat` 相互校验。
- 所有双方同时修改的路径都有明确冲突等级。
- 所有 `KEEP_REBASE`、`REPLACE_UPSTREAM`、`ABSORB_SEMANTIC` 项都有前置依赖和验证要求。
- 不把未提交工作区内容误算成已发布主线，也不遗漏未合并二开的单独附录。
