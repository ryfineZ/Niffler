# Niffler 吸收 Aether 的分阶段实施方案

## 最终策略

保留 Niffler 的发布血统、生产数据语义和产品能力，以届时最新的 Niffler `main` 建立迁移主线；先在当前架构语义移植少量 P0 稳定性修复，再建立 Aether 分层架构兼容层，随后按运行时、协议、数据和界面分批吸收上游能力。

不采用以下方式：

- 不直接合并 `upstream/main`：最终树有 3,309 条不同路径，698 条路径双方都修改且内容分叉，自动合并不能判断计费、调度和协议语义。
- 不把 Niffler 重置成 Aether 后一次性复制二开目录：Niffler 的计费、Niffler Core、支付、返利、迁移历史和生产发布并不集中在独立目录。
- 不按 776 条上游提交顺序逐条 cherry-pick：上游 7 月完成大规模 workspace 分层，旧提交路径和最终路径不同，且合并提交只具有历史意义。
- 不在现有脏工作区或当前计费分支实施：正式开始时从最新已发布 Niffler `main` 创建独立迁移分支，并重新冻结比较点。

## 不得破坏的 Niffler 业务不变量

1. 请求级 `billing_request_admissions` 是调用上游前的资金准入凭证，必须同步、同事务成功；普通候选或观测写入可以异步，它不能异步。
2. 有限钱包只有余额大于 0 才能靠钱包开始请求；有效套餐在钱包欠费时仍能使用；套餐扣到 0 后剩余费用可使钱包变负。
3. 套餐允许的供应商集合必须同时约束准入、真实路由和最终结算，不能在其中任何一步退化为只按模型判断。
4. 历史账单读取已保存的价格和结算事实，不按最新在线价格、倍率或 Provider 配置重算。
5. `enable_new_routing` 命中时，产品策略、上游服务、账号和账号模型能力继续决定权限、售价和可调度范围。
6. 返利只能由旧链路或新账本中的一条路径实际发放；重试、取消和人工处理都必须幂等。
7. 输出前可因容量错误换账号；一旦客户端已见响应头或用户可见事件，不允许重试并拼接另一账号的响应。
8. 用户看到的“首字”使用端到端口径；成功尝试首字继续保留为诊断字段，不能用它替代用户等待时间。
9. 已执行的数据库迁移永不改写或删除；废弃对象通过新增迁移停止写入、归档或删除。
10. Background 维护任务在生产只能有一个有效执行方；双 Frontdoor 不等于双 Background。
11. 生产发布继续使用固定 CI 产物、测试环境晋级和祖先校验；后台在线更新不能绕过发布链。

## 阶段总览

| 阶段 | 目标 | 主要来源 | 上线形态 |
|---|---|---|---|
| M0 | 重新冻结真实起点和运行基线 | 当前审计清单、届时最新 Niffler 主线 | 只读和观测 |
| M1 | 先解决已知连接、数据库压力和耗时口径问题 | Redis 治理、worker 保护、端到端计时 | 小批语义移植，可独立发布 |
| M2 | 建立分层 workspace 和兼容 facade | `8616fe6e` 及其三个前置 facade 提交 | 结构迁移，不改变业务行为 |
| M3 | 迁移数据契约、仓储和运行时基础设施 | data adapters、runtime、缓存、队列 | 影子校验后切换 |
| M4 | 合并调度、流式终态、故障切换和诊断 | scheduler、admission、stream/finalize | 小流量灰度 |
| M5 | 合并协议、OAuth、Provider 和安全能力 | OpenAI/Codex、Claude、Gemini、IP 限制等 | 按协议/Provider 分开灰度 |
| M6 | 在新架构中重放和收缩 Niffler 产品能力 | 计费、Core、提示词、邮件、Grok、内容审查 | 按业务域切换权威读源 |
| M7 | 合并后台体验并清理迁移脚手架 | 上游前端、Niffler 产品页和运维页 | 页面逐项替换 |
| M8 | 生产晋级和稳定观察 | 测试环境、双 Frontdoor、唯一 Background | 分批实例、可回退发布 |

## M0：重新冻结和基线

### 工作

- 等当前计费、提示词和本地双入口等已决定功能按正常发布链进入 `main` 后，记录新的 Niffler 固定提交。
- 获取实施时最新 Aether `main`，重新运行本目录的清单和校验器；当前报告仍保留为 2026-08-12 的设计基线。
- 建立以下生产只读基线：请求量、端到端首字、成功尝试首字、总耗时、换号率、终态缺失率、Redis `connected_clients`、`total_connections_received`、TIME_WAIT、数据库池等待、后台任务延迟、结算失败、返利待处理、钱包负余额。
- 导出数据库迁移版本、表数量、索引、行数和关键约束；备份恢复演练必须在测试库实际执行一次。
- 为 698 条双方分叉路径生成新的冲突清单，确认没有实施期间新增的第三条业务分叉。

### 退出条件

- 新固定点的提交、路径、来源和处置账本全部通过 `validate_audit.py`。
- 测试和生产配置差异有明确清单；密钥值不进入报告。
- 关键指标至少有一个正常业务周期的基线，不能用迁移后的第一天数据反推基线。

## M1：当前架构上的 P0 稳定性移植

M1 不等待完整 workspace 分层，优先降低已知生产风险；每项使用独立分支、独立开关和独立回退。

### M1.1 Redis 固定连接通道

来源：`ab0a90de9` 的行为目标，以及 Aether 最终 `crates/aether-runtime/state/src/redis/` 实现。

实施：

- 在 Niffler 当前 `aether-runtime-state` 结构中建立 fast、stream、blocking stream、admin 固定通道及通道级超时、错误和延迟指标。
- 替换旧树中 4 个运行时文件的 31 处逐次获取连接调用；阻塞流必须有独立连接，不能占住快速命令通道。
- 重连由通道管理，业务调用方不自行循环建连。
- 移植运行时 Redis 压力工具和连接数量断言。
- 保持 Niffler 当前 Redis 持久化配置；是否关闭 AOF/RDB 单独由恢复目标决定。

验收：

- 固定并发下 `total_connections_received` 不随请求数线性增加。
- 网关重启、Redis 短暂不可用和恢复后，连接数回到预期常量范围。
- blocking stream 压力不抬高 fast lane 的 P99 到不可接受范围。
- 失败回退不会把多节点必需状态静默降到单进程内存。

回退：保留旧后端选择开关一个发布周期；回退只切连接实现，不改变 Redis 数据键和业务数据。

### M1.2 数据库压力下保护后台任务

来源：`8966fd6aa`、`576918daa`、`ccfc4cbdd` 的目标。

实施：

- 对邮件发送、日统计补跑、Provider 配额刷新、账号自检、pool score rebuild、历史预占清理和返利重试统一增加数据库池压力门禁。
- 可延迟任务在压力高时延迟或跳过本轮；计费准入、最终结算、支付回调、返利实际发放和用户鉴权不得因此静默丢弃。
- 逐条复核调度热点 SQL 和索引；新增索引使用独立迁移，并检查三种数据库语法及 PostgreSQL 在线创建要求。
- Provider catalog 缓存必须监听 Niffler 上游服务、账号、模型能力和旧 Provider 管理写入的全部失效事件。

验收：正常请求与维护任务并发时，数据库池等待、超时和请求 P99 不劣于 M0 基线；暂停维护任务后能够补跑，且不会重复发钱或重复结算。

### M1.3 端到端首字和总耗时

来源：`a04673a90` 中可独立移植的计时行为。

实施：

- 增加 `end_to_end_first_byte_time_ms` 和 `end_to_end_time_ms`，请求进入网关即开始计时，包含鉴权、准入、排队、选号、失败尝试和换号。
- 保留现有 `first_byte_time_ms` 作为成功尝试或当前候选口径，并在 API 文案中明确区分。
- 首个上游事件不能自动算用户首字；过滤后的控制事件、心跳、空块不结束计时。
- 历史记录字段为空时显示“无端到端数据”，不拿旧 `first_byte_time_ms` 回填伪造。

验收用例至少包含：无重试、一次 10 秒失败后 120 毫秒成功、只有控制事件、HTTP 200 内错误、下游断连、非流式、输出前换号和输出后禁止换号。

## M2：workspace 分层基础迁移

### 原则

M2 只改变依赖方向和文件归属，不顺带改变计费、调度、协议或界面行为。任何“搬文件时顺便采用上游实现”的修改都拆到后续阶段。

### 顺序

1. 先引入 serving、format 和 auth 的兼容 facade，对应 `938f1198`、`b2f596b8`、`63936aa1` 的依赖方向。
2. 按 `8616fe6e` 的最终边界建立 data contracts、data adapters、runtime state、usage runtime、provider transport、AI formats 和 admin/observability 层。
3. 旧路径保留薄 facade，使现有 Niffler 调用方继续编译；禁止再向旧层添加业务。
4. 依次迁移无状态类型、纯转换、仓储契约、数据库适配、运行时、网关编排，最后迁移前端接口生成物。
5. 每移动一个业务域，运行旧路径禁止新增依赖的架构检查。

### Niffler 扩展归属

| 扩展 | 新层归属 | 不能放入的位置 |
|---|---|---|
| 计费准入与结算契约 | data contracts + billing domain；网关只编排 | 通用 candidate queue |
| Niffler 产品策略和账号能力 | data contracts/repository；routing 只读快照 | Provider transport 凭证层 |
| CPA/sub2api/授权文件解析 | OAuth import adapter | 数据库仓储函数 |
| Grok OAuth | Provider/OAuth adapter | 通用 OpenAI 格式转换 |
| 受管理提示词 | AI serving policy + 协议原生格式转换 | 前端或请求正文临时拼接 |
| 内容审查 | 独立 policy service | Provider 账号健康判断 |
| 邮件队列 | async task/worker + data repository | HTTP handler 同步发送 |
| 公共站点和生图工作台 | Niffler frontend product | 上游 admin 组件层 |
| 发布、监控和拓扑 | deploy/operations | 应用在线更新模块 |

### 退出条件

- 架构检查证明依赖只向内层流动，旧 facade 没有业务实现增长。
- 当前 Niffler 全部业务回归在行为不变的前提下通过。
- 编译产物、数据库迁移列表、公开 API 和前端路由与 M2 前一致；差异都有书面例外。

## M3：数据、缓存和队列基础设施

### 数据迁移模板

所有持久化对象统一使用：新增结构 → 回填 → 双读比较 → 切权威读源 → 停旧写 → 稳定观察 → 归档/删除。资金类对象不做双实际写入，只允许“单权威写入 + 旁路对账”。

### 必做项

- 将三数据库仓储迁入上游 adapter 边界，保持 Niffler 现有迁移版本和业务字段。
- 对 migration ID/文件名冲突建立显式映射；绝不改写已上线文件来迎合上游序号。
- 当前双树迁移清点显示：Niffler 有 134 个 SQL 文件/62 个版本，Aether 有 109 个 SQL 文件/58 个版本；共同的 67 组“版本 + 数据库”中，64 组内容一致，3 组共同基线 `20260403000000` 内容不同。Niffler 对已应用迁移的校验按版本放行并只告警 checksum（校验和）漂移，因此不能把“服务能启动”当作 schema 相同；M3 必须对三份基线做结构差异和真实数据库目录对账。
- 吸收 portable SQL parity 和生成 schema 检查，确保 PostgreSQL/MySQL/SQLite 的约束、索引和默认值一致。
- 引入鉴权、API Key、routing group、Provider catalog、candidate page 等缓存时，为以下 Niffler 写入补齐失效：产品策略、Key 绑定、服务、账号、账号模型能力、分组倍率、Provider 模型、钱包状态和套餐权益。
- 普通请求候选、路由尝试、结算影子快照可进入分级队列；资金准入、最终结算、支付到账和返利发放继续同步持久化。
- worker 自动扩缩先设保守上限，并保证生产唯一 Background；Frontdoor 不启动同一消费组的维护任务。

### 数据一致性门禁

- 新旧读取结果按主键、金额、状态和时间窗口逐项比较，不能只比行数。
- 金额使用数据库精确数值和原有舍入规则；浮点比较不能作为结算一致性判断。
- 回填必须可重入、可限速、可暂停，并记录最后处理主键和失败原因。
- 切换前冻结待处理支付、返利、预占、结算队列快照；切换后逐项核对数量和金额。

## M4：调度、流式和请求运行时

### 调度

- 吸收 candidate page、upstream admission、stage metrics、调度缓存和请求诊断。
- 候选集合先应用 Niffler 资金准入允许的供应商，再应用产品策略的服务/账号/模型能力，最后进入上游评分和并发准入；顺序不得颠倒。
- 新缓存的键必须包含会影响路由或售价的 Niffler 维度，或引用可失效的版本号。
- pool score、健康、冷却和 Niffler 风险事件保持不同语义；普通 5xx 不自动扩大为 Provider 级冷却。

### 流式和故障切换

- 采用上游最终的终态单调、HTTP 200 内错误、SSE 控制事件、断连 drain、取消和 watchdog 规则。
- 将 Niffler 的预读首字和容量错误换号接入同一个响应提交状态机，删除独立分支状态。
- 状态机至少区分：未提交、已提交响应头但无可见正文、已见控制事件、已见用户可见事件、终态、下游断开。
- 是否允许换号由“用户可见输出是否已提交”决定，而不是仅看是否从上游收到过字节。

### 退出条件

- 协议终态、换号、取消和计时组合测试通过。
- 调度候选逐项证明没有越过套餐供应商范围或 Niffler Core 账号能力。
- 请求诊断接口对普通用户隐藏原始凭证、上游账号身份、敏感正文和内部错误。

## M5：协议、OAuth、Provider 和安全

每个协议单独实施，不能用一个“同步 Aether 协议”合并请求包住全部变化。

### 建议顺序

1. API Key IP 限制：数据、鉴权、用户/管理 API、导入和 UI 必须同批完成，避免只存不验或只验不可清空。
2. OpenAI/Codex/Responses：先标准字段和终态，再 Search、Compact/V2、continuation history、Agent Identity、processing tier 和图片能力。
3. Claude：thinking、tool result、system guidance、context management 和 Claude Code 跨格式。
4. Gemini/Antigravity：native contents、v1internal、Interactions、项目元数据、配额和内置工具。
5. OAuth 生命周期和 Provider 管理：状态刷新、凭证隔离清理、批量动作、transfer limit；最后接回 Niffler 导入适配器。
6. Windsurf、Kiro、DeepSeek、Aliyun 等只按明确运营需求启用；未启用实现可以随后吸收，但不开放配置入口。

### 协议测试矩阵

维度至少包括：客户端格式 × 上游格式 × 流/非流 × 工具/图片/音频 × reasoning × system/developer 注入 × 无重试/换号 × 成功/HTTP 错误/流内错误/断连。每个实际支持的组合都必须有请求快照、响应快照、用量、首字和结算断言。

### 拒绝项

- 不因普通 403、网络失败或临时配额错误自动删除 OAuth 凭证。
- 不开放后台在线部署。
- 不把未运营 Provider 的 OAuth、刷新任务和告警默认启用。

## M6：Niffler 产品能力重放和收缩

### 必须保留并迁入新层

- 请求级计费准入、套餐供应商范围、原子结算、支付、欠款随套餐订单结清。
- Niffler 产品策略、上游服务/账号/账号模型能力和灰度权威读源。
- 返利账本幂等、旧明细兼容和人工处理。
- CPA、sub2api、嵌套 ChatGPT 授权、Grok OAuth 和 CCSwitch。
- 分组提示词、异步邮件、用量/利润展示、公共站点、生图工作台和受保护发布。

### 应删除或还原

- 删除请求前真实金额预占运行分支和可编辑开关；历史表、事件、读取和过期清理在 active 记录清零且审计归档前保留。
- 风险动作入口暂时只允许 `record_only`；`pause_scheduling`、`disable_account` 在没有执行器、恢复规则和审计闭环前隐藏并拒绝保存。
- 删除按最新价格重算历史金额、使用缓存决定资金放行、套餐静态模型编辑和旧 `allow_wallet_overage` 业务开关。
- 迁移完成后将 readiness、稳定观察、旧接口投影和回滚证据移到高级运维；确认不再需要后停止新增影子记录。

### 需要业务决定

- 内容审查的适用对象、失败策略、费用承担和正文留存。
- 旧 `hub`、`cf` 外部入口是否可删除，必须用真实流量证明。
- 未运营的上游 Provider 是否值得承担长期维护。

## M7：前端和运维收口

- 在上游新版 admin 组件与服务端分页接口上逐页重放 Niffler 管理能力，不覆盖公共首页、生图工作台和品牌页面。
- 页面必须同时适配处理、不可用、空内容、错误和权限不足状态。
- 后台默认展示端到端首字；展开请求诊断后显示成功尝试首字、失败尝试和各阶段耗时。
- Niffler Core 日常产品配置与迁移工具分离导航。
- Telegram、S3、Bark、Server 酱等先统一事件模型，再决定渠道；不同时运行多套相同告警。
- 上游版本检查可保留，只读显示新版本；部署按钮不接入生产执行。

## M8：发布、灰度和回退

### 发布顺序

1. 独立测试环境执行全量迁移、回填和恢复演练。
2. 影子流量验证协议、调度和计时；影子流程不得实际扣费或发返利。
3. 先发布唯一 Background，确认没有重复消费，再发布一台 Frontdoor。
4. 小比例 API Key/产品策略灰度，观察完整业务周期。
5. 扩到第二台 Frontdoor；两台版本、配置和迁移版本一致后再扩大灰度。
6. 所有门禁通过后才关闭旧读源或旧 facade；关闭和删除分两个版本完成。

### 自动停止条件

- 出现重复结算、重复返利、套餐供应商越界、支付回调金额不一致或迁移约束损坏。
- 用户端到端首字、错误率或终态缺失率显著劣于 M0 基线。
- Redis 连接总数继续随请求线性增长，或数据库池等待/超时持续升高。
- Background 同一任务出现两个活跃租约/消费者，或补跑任务持续堆积。
- 协议响应在输出后发生跨账号重试。

### 回退边界

- 代码回退只能退到兼容新 schema 的上一版本；一旦执行新增迁移，不用删除列/表作为紧急回退。
- 权威读源切换用独立开关回退；资金和返利不能同时双写两个权威实现。
- 队列消费者回退前先停止领取新任务，等待或转储在途任务，再启动旧消费者。
- Redis 通道回退不删除键；缓存格式变更必须使用版本化命名空间。
- 前端可以先回退展示，后端字段在整个稳定观察期保持兼容。

## 验证矩阵

| 领域 | 最低验证 |
|---|---|
| 数据 | 三数据库迁移、空库、升级库、重复执行、约束/索引、回填断点和恢复 |
| 计费 | 钱包正/零/负、套餐足/不足/过期、并发最后一批、供应商越界、幂等结算、支付重复回调 |
| 返利 | 新旧路径互斥、重复任务、取消、失败重试、金额总账 |
| 调度 | 产品策略、Key 绑定、模型倍率、服务/账号能力、缓存失效、冷却和并发 |
| 流式 | 协议终态、控制事件、流内错误、断连、超时、换号、输出提交边界和耗时 |
| Redis | 固定连接数、通道隔离、重连、Redis 重启、连接统计和压力 |
| Worker | 数据库压力、唯一消费者、扩缩容、停机续跑、死信和重复处理 |
| 安全 | IP 限制、权限、PII、正文/错误留存、OAuth 凭证删除边界、诊断接口 |
| 前端 | 服务端分页、金额和首字口径、移动端、权限、空/错/加载状态 |
| 发布 | 固定提交产物、test 晋级、外部数据库预检、单 Background、双 Frontdoor、回退版本 |

## 完成定义

只有同时满足以下条件，才能宣称“已吸收 Aether”：

- 本报告标为吸收的每条上游非合并提交均有实现提交、等价测试或明确的后续阶段记录。
- 所有 Niffler `KEEP`/`KEEP_REBASE` 能力均有迁移后入口和回归测试；`SPLIT` 中删除的行为已不可从 API、配置或后台重新启用。
- 所有 `REJECT` 项有自动检查或权限边界防止误引入。
- 新旧数据对账、资金总账、返利总账和请求状态在稳定观察窗口内一致。
- 生产指标不劣于 M0 门禁，且回退演练真实通过。
