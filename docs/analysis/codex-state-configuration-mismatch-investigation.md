1. 核对两台应用版本及共享诊断记录，定位可复现账号。

## 影响及界面问题

1. 后台 `current_plan` 在代理配置变化后拒绝继续使用旧会话，随后移除旧会话。停止旧出口补采符合出口绑定规则；由新正式请求登记新出口后再补采。本次线上已观测到新出口登记和探测结果。
2. 诊断保留旧记录 24 小时，配置不匹配时统一显示 `configuration_changed`，覆盖该条记录的具体采集结果；前端又将其翻译成“凭据或配置已变化”，用户无法判断到底变了什么，也无法据此知道当前出口是否有可用 State。
3. `usePoolCodexState.ts:17-24` 每次账号列表引用变化都会清空全部 State 并显示加载，再逐账号填回。账号周期用量缺失时，号池会按 1 秒间隔最多重载 5 次，搜索、翻页等也会触发列表替换。此机制会造成状态重绘，与采集是否成功无关；没有独立的 State 持续轮询。这里是代码确认的重绘机制，未通过浏览器录制量化用户当前页面的实际频率。
4. 整份 transport 摘要还包含名称等无关字段，这是额外的设计缺陷，但不是此次两账号提示的实际原因，不能混为一谈。

## 定位阶段提出的修复范围

- 账号行以当前出口的结果为主：暂无采集记录、采集中、采集失败、State 可用；最近请求是否注入独立显示。
- 旧出口历史放详情，不再用历史配置变更代替当前出口采集状态。确实发生变化时区分出口变化、凭据变化、账号停用。
- 后台刷新保留已有显示，仅更新发生变化的账号单元格；补齐独立状态轮询、离页取消和重叠请求保护。
- 配置比较收敛到真正影响 State 身份、模型权限和出口的字段；仍严格保证不同出口、凭据不混用。
- 采集错误拆分执行失败、超时、复核取消，避免所有问题都显示为“连接失败”。

验收重点：旧代理切新代理、直连切代理均显示新出口真实采集结果；凭据不变不提示凭据失效；真正轮换凭据或停用仍停止旧会话；轮询时标签不清空、不重排；成功/失败更新可见且不触发重复采集。

## 请求成功与采集失败的对照（2026-09-20 17:55–18:01，UTC+8）

用户反馈使用统计有很多成功记录，但账号一直没有 State。本轮只读核对共享 Redis、生产 PostgreSQL 与当前代码，未发起真实探测，未修改生产配置或数据。

- 采样时，Pro 号池同一个账号近两小时有 22 条 `gpt-6-astra` 的 `completed / 200` 记录，22 条均有输出 tokens 且没有 error_message。另有 13 条 `gpt-5.5` 成功记录；该模型不在当前 State 适用名单中。统计是采样时快照，后续请求仍在增加。
- 同账号对应 Redis 诊断索引已核对一致。最新 `gpt-6-astra` 采集结果为 `timeout / accepted=false`，最近正式派发记录为 `passthrough / HTTP 200`。8 个当前及历史模型/出口组合均无缓存；各组合最近一次采集结果为 5 个旧 `transport_error`、1 个 `timeout`、2 个 `invalid_state`。这些是各组合的最后一次结果，不是全部探测次数。
- 当前实现将采集与正式生成分开。仅 `collect_attempt` 在探测完整成功且响应 State 通过结构、块数和时间校验后写缓存；`Prepared::observe` 不保存正式请求返回的新 State。普通模式采集失败后仍可转发。因此同账号能生成成功与没有缓存可以同时成立。
- 生产配置的探测次数为 6，兜底配置缺失时按普通模式，轮次间隔缺失时为 30 秒。代码的最多 6 次共用整轮 20 秒，并非每次 20 秒；一次超时可耗尽本轮预算，后续次数不会执行。前台和后台共用这个限制。
- `probe_once` 先读流至 EOF，再检查完成事件。现有摘要没有首字节时间、完成事件时间、收到 State 与否、具体执行错误阶段，因此目前不能确定此次超时发生在连接、生成还是读流结束阶段，也不能断言所有旧 `transport_error` 都是超时。
- 使用统计抽样没有留存响应正文，也没有持久化的 `x-niffler-turn-state` 值。输出用量支持这些成功记录并非仅有 HTTP 200；但无法凭现有存档逐条复核正文，不能证明所有历史“成功”都无终态错误。同时间窗已有 `failed / 503` 和 `failed / 500`，不能说当前系统把所有失败都显示为成功。

后续修复应先补采集阶段的无敏感信息诊断，明确超时位置；再将前台等待限制与后台每次尝试/整轮预算分开。不能以延长前台等待的方式解决后台采集问题，也不能把 HTTP 200 直接当成合格 State。是否增加正式成功回包的 State 回收需另行明确完整成功、同账号/凭据/出口及并发发布边界，本轮未修改此行为。

## 后续执行计划（2026-09-20 已授权执行）

目标：管理员能区分正式生成结果、是否注入 State、采集失败原因；普通请求保持可用，后台具有真实的多次采集机会。沿用账号当前允许的出口、现有模型范围和严格模式的显式选择，不新增出口池、不批量重写历史请求。

### 第一批：诊断、采集和请求记录闭环

1. **补齐失败证据。** 将当前 `Result<_, ()>` 收敛成不含秘密的错误类别，记录轮次/尝试序号、是否实际派发、响应头和首字节耗时、完成事件是否到达、总耗时，以及 State 缺失/结构不符/块数不符/过期等原因。已取得 HTTP 200 后读流超时，应保留已知 HTTP 状态，不能再统一显示为状态 0。正式请求也记录返回 State 是否存在和是否通过校验，先取得是否值得被动回收的证据；不记录 State 原文、认证头或用户正文。
2. **分开普通请求等待与后台采集。** 普通模式命中合格缓存则注入；未命中时登记活跃会话并继续正常转发，交由已有受监管的后台循环补采。严格模式仍保留明确的有界等待和无缓存拒绝语义。后台先以每次最多 20 秒、最多配置次数（线上为 6）的独立网络预算实施，6 次网络总上限为 120 秒，配置校验与存储操作另有有界开销；单次时限根据第一步观测复核，不能假定 20 秒适合所有真实响应。普通轮次结束后仍按现有 30 秒默认间隔重试，认证拒绝和限流立即结束并使用原账号保护。
3. **同时修正长轮次的并发边界。** 现有采集租约仅 30 秒，后台外层也只有 25 秒；与新预算一并调整。长轮次需有租约续期和丢失所有权后的取消/禁止发布，不能只改 timeout 常量。全局采集槽不被单账号整轮独占，尝试之间允许其他活跃账号获得机会；配置/凭据/出口变化、功能关闭和网关退出都必须停止相关任务。使用已有监督生命周期，不创建游离任务。
4. **以完整协议终态结束探测。** 增量解析 SSE，收到完整 `response.completed` 并通过 State 校验即可完成；流错误、缺失完成事件、截断和体积超限分别处理。避免已收到完成事件后继续等连接 EOF。此项修复代码边界，不能反推当前生产超时已经确认发生在 EOF 阶段。
5. **请求记录显示两项独立结果。** 保留现有生成成功/失败状态，增加本请求“已注入 / 未注入 / 不适用 / 记录不可用”的 State 使用信息及必要原因，优先复用现有请求元数据。账号行继续在号池列表，展示可用缓存、最新采集结果和实际尝试次数；轮询保持稳定。旧记录没有字段时显示未记录，不能补造注入状态。回归核验现有容量错误修复：HTTP 200 流中出现 `response.failed` 必须最终归档失败。

第一批验收：模拟首次探测超时后第二次仍有独立机会；普通请求不等待后台整轮；收到 completed 后连接挂起也能结束采集；失败/不完整响应不入缓存；超过 30 秒的轮次不重复发布；前后台、双机同出口合并；旧凭据迟到不能影响新凭据；不同机器直连仍隔离；页面能区分生成失败与未注入。执行直接相关后端/前端测试、构建和代码 review。

### 第二批：按证据决定是否回收正式回包的 State

- 如果第一批观测确认正常生成回包含有合格 State，却因没有专门探测成功而未保存，再增加被动回收；若正常回包同样缺失或不合格，继续处理探测失败原因，避免加入没有实际收益的缓存写入路径。
