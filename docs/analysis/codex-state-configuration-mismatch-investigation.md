# Codex State「凭据或配置已变化」线上定位

## 目标与边界

目标：确定线上提示的实际触发原因、影响范围及是否影响后台补采；同时区分前端重新加载与真实采集进度。只读排查，不触发采集、不修改生产账号或运行时缓存，不记录凭据和 State 原文。

## 排查顺序与验收

1. 核对两台应用版本及共享诊断记录，定位可复现账号。
2. 比较诊断保存的凭据/配置摘要与当前数据，区分真实凭据变化、停用及配置摘要误判。
3. 结合正式请求与后台补采路径验证影响；不能恢复历史字段时明确证据边界。
4. 记录可核验结论及最小修复范围。若需实现，先明确行为与回归条件。

| 账号 | 登记旧记录时 | 排查时配置 | 凭据摘要 |

验证方法：在只读脚本内存中按生产代码的字段顺序构造当前 transport，先确认当前摘要与新请求登记的摘要精确一致，再只替换 `key.proxy` 为旧出口配置。两个账号的完整 SHA-256 都与历史记录精确匹配，其余字段保持不动。下表仅记录摘要前缀方便追溯，比较时使用完整摘要。

| 账号 | 当前摘要前缀 | 仅还原代理后 / 历史摘要前缀 |
| --- | --- | --- |
| 账号 A | `d8fac9729d9b` | `8cba8843c9c6` |
| 账号 B | `d1ad3adc984b` | `cb5a4918da73` |

因此本次原因不是凭据轮换、账号停用、版本不一致或名称/倍率改变。两个账号的 provider、endpoint、key 均启用。不能据此判断是谁、通过哪次操作修改了代理，现有诊断不保存操作者。

### 当前采集情况

- 初次采样有 2 个账号、6 组模型/出口记录；两台机器读到相同记录，未发现可用 State 缓存。
- 排查期间已有新的正式请求：北京时间 16:44:36、16:46:01，分别为上述两账号登记新代理记录。新记录配置摘要与当前数据库一致，证明可以在新出口重新登记，并非永久卡在旧配置。
- 后续采样共 8 组记录，仍无可用 State 缓存。各组最近一次采集结果为 6 条 `transport_error`、2 条 `invalid_state`；两个新出口记录也为 `transport_error`。
- `transport_error` 当前合并了执行错误、超时和派发前复核失败，不能仅据该字段断定是代理连接失败。此次已定位配置变化的具体原因，未定位采集传输失败的更细原因。
- 两条新记录最近正式请求模式为 `passthrough`，即未注入缓存 State。其记录的 HTTP 200 不能单独证明流式业务成功。

“旧记录”是旧请求/采集的诊断记录，不能解释为“以前一定采集到合格 State”。

## 影响及界面问题

1. 后台 `current_plan` 在代理配置变化后拒绝继续使用旧会话，随后移除旧会话。停止旧出口补采符合出口绑定规则；由新正式请求登记新出口后再补采。本次线上已观测到新出口登记和探测结果。
2. 诊断保留旧记录 24 小时，配置不匹配时统一显示 `configuration_changed`，覆盖该条记录的具体采集结果；前端又将其翻译成“凭据或配置已变化”，用户无法判断到底变了什么，也无法据此知道当前出口是否有可用 State。
3. `usePoolCodexState.ts:17-24` 每次账号列表引用变化都会清空全部 State 并显示加载，再逐账号填回。账号周期用量缺失时，号池会按 1 秒间隔最多重载 5 次，搜索、翻页等也会触发列表替换。此机制会造成状态重绘，与采集是否成功无关；没有独立的 State 持续轮询。这里是代码确认的重绘机制，未通过浏览器录制量化用户当前页面的实际频率。
4. 整份 transport 摘要还包含名称等无关字段，这是额外的设计缺陷，但不是此次两账号提示的实际原因，不能混为一谈。

## 定位阶段提出的修复范围

- 账号行以当前出口的结果为主：暂无采集记录、采集中、采集失败、State 可用；最近请求是否注入独立显示。
- 旧出口历史放详情，不再用历史配置变更代替当前出口采集状态。确实发生变化时区分出口变化、凭据变化、账号停用。
- 后台刷新保留已有显示，仅更新发生变化的账号单元格；补齐独立状态轮询、离页取消和重叠请求保护。
- 配置比较收敛到真正影响 State 身份、模型权限和出口的字段；仍严格保证不同出口、凭据不混用。
- 采集错误拆分执行失败、超时、复核取消，避免所有问题都显示为“连接失败”。

验收重点：旧代理切新代理、直连切代理均显示新出口真实采集结果；凭据不变不提示凭据失效；真正轮换凭据或停用仍停止旧会话；轮询时标签不清空、不重排；成功/失败更新可见且不触发重复采集。

前次定位阶段仅调查和记录，未改业务代码、未提交、未部署。后续修复实施如下。

## 修复实施（用户已要求修复）

- 诊断新增稳定记录 `id`、`current` 和细分历史原因；旧版 `configuration` 摘要保留，新增可选摘要字段，支持滚动发布期间旧记录读取。只有当前记录计入账号行可用数、采集结果及最近注入状态；没有当前记录时显示“当前出口暂无采集记录”，历史仍可在详情查看。
- 新摘要排除名称、网站、倍率、调度优先级、并发/重试/超时等与 State 身份无关的字段；权限、凭据和出站配置继续参与检查。新摘要排序 JSON 对象，避免相同配置仅键顺序改变导致误判。旧版记录继续严格校验旧摘要，不推测其缺失的配置。
- 凭据变化、代理配置变化、账号/端点停用分别标记；旧版记录只在现有元数据能证明出口不同的情况下标记出口变化，否则保留“历史配置已变化”。

- 账号行优先显示可用 State，其次认证/限流、最近采集失败、等待补采；冷却不掩盖上一轮失败。详情把历史记录折叠，刷新不清空已有内容。
- 本次不更改正式请求的采集、注入、兜底及计费规则，不改变候选出口；不把诊断页读取变成采集操作。采集错误先将超时单列，旧 `transport_error` 文案不再断言一定是连接错误。
