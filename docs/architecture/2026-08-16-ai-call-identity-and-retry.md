# 模型调用编号、自动换服务与收费记录

## 目标

- Niffler 每收到一次模型调用，都生成独立的内部调用编号；客户端跟踪号只用于关联排查。
- 同一次调用只确定一次收费方式。系统自动换服务时沿用首次决定，不因余额或套餐随后变化而中断。
- 已经失败的同一服务账号不在另一条执行流程中被重复调用。
- 每次模型调用都留下成功或失败记录，失败不能消失在使用记录之外。
- 保持现有 Codex OAuth 指纹收敛行为：同一上游账号继续使用稳定设备、会话和任务身份。

## 非目标

- 不修改历史记录、历史收费结果或生产钱包数据。
- 不要求 WorkBuddy 改变跟踪号或会话号的使用方式。
- 不使用指纹、会话号或任务号判断两次调用是否是同一次收费请求。
- 不在本次增加客户端主动重放同一结果的功能。

## 业务规则

### 调用编号与跟踪号

1. Niffler 每收到一次 HTTP 模型调用，都生成新的内部调用编号。
2. 客户端传入的跟踪号、请求号、会话号和任务号可以重复，但不能替代内部调用编号。
3. 使用记录、收费决定和服务执行记录全部使用内部调用编号关联。
4. 管理员可以按内部调用编号精确查询，也可以按客户端跟踪号查看同一链路下的多次调用。

### 收费决定

1. 每次调用在第一次选择可用服务时，根据当时的钱包、套餐和模型确定收费方式。
2. 同一次调用后续自动换服务时直接沿用首次收费决定，不重新读取余额或套餐后推翻原决定。
3. 首次收费决定必须在调用上游前保存成功；保存失败时停止调用上游。
4. 如果同一内部调用编号再次出现，且用户、API Key、钱包或模型不同，系统停止处理并告警；资金余额和套餐剩余额属于首次决定内容，不用于判断编号冲突。

### 自动换服务

1. 第一个服务失败后，可以尝试尚未使用的其他可用服务。
2. 已失败的相同供应商、地址、账号和上游模型组合不能被另一条执行流程再次调用。
3. 系统明确安排的同账号再次尝试必须沿用原调用，并增加尝试次数；不能从第一次重新开始。
4. 全部服务失败后，只向客户端返回一次失败，并结束本次调用。

### 使用记录与收费

1. Niffler 确认路由属于模型调用后，必须立即向数据库写入“处理中”记录并等待写入成功；写入失败时不再继续收费判断或调用模型。
2. 第一次收费判断和调用上游前必须已经存在使用记录。调用结束时必须更新为成功、失败或取消；任何收费判断、服务选择或内部处理错误都必须完成记录。
3. 没有调用上游的失败记录金额为零，收费状态为作废。
4. 最终成功时按现有实际用量规则结算一次；全部服务失败时不向用户收费。失败服务产生的上游成本只进入平台成本记录。
5. 当前请求流程不预占、冻结或预扣钱包金额；请求级收费决定只记录本次调用允许使用的付费方式和服务范围。

### 统一失败返回

1. 模型请求在建立内部调用编号后，任何成功或失败都必须经过同一个结束处理。
2. 错误响应必须返回内部调用编号，客户端跟踪号继续作为独立的链路查询信息。
3. 普通上游服务返回的同名调用编号不得覆盖 Niffler 生成的编号；只有经过认证的内部网关转发才能传递已有内部编号。

### 与 Codex OAuth 指纹收敛的关系

1. 内部调用编号回答“这是 Niffler 收到的第几次调用”，每次调用都不同。
2. 指纹收敛回答“上游看到的是哪个设备、会话和任务”，同一账号和任务可以跨多次调用保持稳定。
3. 同一任务的聊天、压缩和图片调用可以共享上游任务身份，但在 Niffler 中分别留下真实调用记录。
4. 同一次调用更换 Codex OAuth 账号时，新账号使用自己的稳定身份，不能沿用原账号指纹。

## 影响范围

- 网关入口：生成内部调用编号，并单独保存客户端跟踪号。
- 模型调度：同一次调用共享收费决定和已经使用过的服务清单。
- 使用记录：先登记调用，再由所有返回路径完成记录。
- 收费决定与最终结算：只使用内部调用编号，不再使用客户端跟踪号。
- Codex OAuth 指纹收敛：保持现有上游身份生成和改写规则。

## 上线与兼容

1. 现有 `request_id` 字段直接保存新的内部调用编号，客户端跟踪号和客户端请求号保存在现有请求信息中；本次不改表结构，也不改历史记录。
2. 两台 Frontdoor、Background 和内部转发链路使用同一版本后，再统一重启服务，避免同一时间出现两套编号和收费行为。
3. 历史记录继续按原编号查询；新记录按内部调用编号精确查询，也能从请求信息中找到原跟踪号。
4. 后续只有在大量按跟踪号搜索出现性能问题时，才单独增加数据库索引；该索引不影响本次正确性修复。

## 验证方式

- 相同客户端跟踪号连续发送两次调用，生成两个内部调用编号和两条使用记录。
- 第一次服务失败、第二次服务成功时，只保留一次用户调用和一次最终结算。
- 同一次调用换服务期间钱包或套餐变化，仍沿用首次收费决定。
- 不同执行流程不能重复调用已经失败的相同服务账号。
- 收费判断前失败、没有可用服务和全部服务失败都立即显示失败记录，金额为零。
- 上游响应带有同名调用编号时，客户端、访问日志、使用记录和收费记录仍使用网关生成的编号。
- 同一 Codex OAuth 任务的聊天、压缩和图片继续保持稳定上游身份，不同独立调用不合并使用记录。
- PostgreSQL、MySQL、SQLite 和内存实现遵守相同规则。
