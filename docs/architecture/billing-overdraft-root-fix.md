# 有限钱包持续透支根治方案

## 目标

- 钱包真实余额小于等于 0 时，钱包不能授权新的付费请求；小于 0 时还不能购买、续购或自动续费套餐。
- 钱包欠费不使已有套餐失效；本次模型和实际供应商属于有效套餐且窗口仍有余额时，请求可以继续使用套餐。
- 合法开始的最后一笔或最后一批请求继续按真实费用结算。套餐只扣到 0，超出部分扣钱包，钱包可以因此变得更负。
- 套餐直接选择供应商；可用模型由所选供应商当前有效的模型关系动态决定，不再维护需要人工同步的静态模型清单。
- 请求准入、实际供应商路由和最终结算使用同一份请求级资金决定。
- 管理端和用户端显示钱包真实有符号余额，负数不能显示为 0。
- 修复不能增加金额预占、用户级并发限制、输出 Token 限制或其他模型能力限制。

## 非目标

- 不保证最后一批请求只产生一笔或固定金额的欠费。没有金额预占和串行化时，同时通过准入的请求都可能成为最后一批。
- 不重放历史套餐窗口，不修改原始使用记录，不追缴本次缺陷造成的额外使用。
- 本次本地实现和验证不自动修改生产钱包；补偿必须在修复上线并确认异常扣款停止后另行冻结名单。

## 业务规则

### 请求准入

1. 无限钱包继续按现有规则使用。
2. 有限钱包的真实余额按“充值余额 + 赠款余额”计算并保留正负号。只有余额大于 0 时，才可以作为按量支付来源。
3. 有限钱包余额小于等于 0 时，钱包支付不可用；当前请求存在适用且未耗尽的已有套餐时仍可准入。
4. 套餐必须同时满足：权益有效、当前窗口有余额、实际全局模型由套餐所选供应商当前提供、此次实际供应商属于该套餐范围。
5. 无关、过期或已耗尽的套餐不能覆盖钱包拒绝。
6. 费用预估只用于界面提示和监控；缺少最大输出量或无法估算费用不能成为放行理由，也不能成为拒绝正常请求的理由。

### 最终结算

1. 结算只接受调用上游前已经持久化成功的请求级计费准入。
2. 套餐按最早到期、最早获得、权益 ID 的固定顺序消耗。
3. 每个套餐窗口只扣到 0，不允许套餐余额变成负数。
4. 套餐合法准入请求的最终费用超过套餐剩余额度时，剩余费用继续扣钱包，即使钱包在请求开始时已经为负。
5. 旧套餐的 `allow_wallet_overage` 配置不再决定是否补扣钱包。套餐不足部分必须扣钱包，不能免费，也不能因该配置关闭而拒绝余额大于 0 的正常请求。
6. 不再记录独立的“套餐超用金额”；套餐扣款、钱包扣款和钱包结算后余额已经完整表示本次费用。
7. 请求没有有效准入、实际供应商越界和结算重复时，不得继续扣钱包；保存计费异常并告警。

### 套餐购买

1. 钱包真实余额小于 0 时，创建套餐支付订单必须失败。
2. 钱包真实余额小于 0 时，支付回调、续购和自动续费发放套餐也必须失败或进入人工处理，不能只依赖创建订单时的检查。
3. 同一用户同一时刻只能有一个生效套餐。已有套餐生效期间不能购买其他套餐；同一套餐续费只能顺延有效期，不能创建时间重叠的第二份权益。
4. 创建订单、支付发放和管理员修改权益时间都必须在数据库事务内复核单套餐限制，防止并发操作或人工编辑产生重叠套餐。
5. 已经生效的套餐继续有效。
6. 充值使钱包恢复到 0 或正数后，恢复套餐购买资格。

## 数据结构

### 套餐供应商关系

- `billing_plan_providers(plan_id, provider_id)`：套餐模板当前选择的供应商。
- `user_entitlement_providers(user_entitlement_id, provider_id)`：购买或发放时保存的供应商范围快照。
- 两张表使用联合唯一键并建立反向供应商索引。
- 供应商被有效套餐或权益引用时禁止物理删除；停用供应商或移除模型只影响后续新请求。
- 旧套餐的静态模型 ID 不能可靠反推出供应商。迁移只创建待确认状态，不自动猜测；管理员确认供应商后才能切换到新规则。

### 请求级计费准入

新增 `billing_request_admissions`，每个 `request_id` 只能创建一次，至少保存：

- 用户、API Key、钱包和全局模型。
- 钱包准入时的真实余额、钱包是否可用于本次按量支付。
- 命中的套餐权益和固定消耗顺序。
- 本次允许的供应商集合。实际尝试和最终使用的供应商分别保存在服务尝试记录和使用记录中；一次请求可能在允许范围内重试多个供应商，不能把第一个供应商写成不可变的最终供应商。
- 命中的套餐权益及其供应商范围。即使业务只允许一个生效套餐，也要保留这层对应关系，确保供应商切换后只使用该套餐允许的范围。
- 是否允许套餐不足后扣钱包。
- 准入时间、状态、拒绝原因和结构版本。

该记录不是金额预占，不冻结余额，也不阻塞其他请求。有限钱包和套餐请求写入失败时必须停止调用上游；无限钱包和明确免费请求使用各自独立规则。

生产环境必须启用钱包和计费数据仓库。只有明确关闭计费功能的开发或测试环境可以跳过请求级计费准入；不能把“钱包仓库未配置”当作生产环境的放行条件。

## 请求流程

1. 鉴权阶段只处理身份、账户、API Key 和钱包基础状态，不再使用所有套餐聚合余额覆盖钱包拒绝。
2. 协议解析完成后得到实际全局模型。
3. 调度查询当前可用供应商，同时读取 PostgreSQL 中的钱包真实余额和该模型可使用的套餐窗口。
4. 按实际全局模型查询套餐：如果套餐供应商能提供当前模型，只在这些套餐供应商范围内选择和重试；当前模型不属于套餐时，正余额钱包可以选择其他供应商按量支付。请求付款决定保存当前套餐权益及其全部可用供应商，结算使用使用记录里的最终供应商校验并核销套餐。旧套餐尚未补录供应商时，继续按旧模型范围判断，并在请求付款决定中明确保存“旧套餐按当前模型允许任意实际供应商”，不能产生无付款决定的请求。
   服务分批读取时，套餐是否适用只根据当前全局模型和剩余额度判断，不能根据当前批次是否碰巧包含套餐供应商判断。首次读取的资金结果在同一请求后续批次中复用，不能每读取一批服务就重新访问数据库。
5. 调用上游前，将计费准入与当前请求候选写入放在同一数据库事务和网络往返中。
6. 流式和非流式请求都必须走同一准入函数；协议转换和 Codex 特殊路径不能删除该步骤。
7. 结算事务读取请求级准入，校验实际供应商，锁定钱包和命中的套餐窗口，然后执行套餐扣款与钱包补差。

## 缓存与并发

- 钱包余额和套餐窗口余额的最终放行依据必须来自 PostgreSQL 已提交状态，不能使用三秒过期缓存。
- 供应商、模型和供应商模型关系可以按目录版本缓存，并在管理配置变化时失效。
- 准入不锁定资金。并发请求可能同时看到套餐仍有余额并一起通过，这些请求都属于合法最后一批。
- 结算继续使用短事务和行锁保证单次扣款、套餐不为负及幂等。

## 接口与界面

- 钱包接口返回 `actual_wallet_balance`、`spendable_wallet_balance`、`debt_usd` 和 `billing_state`。
- 旧 `balance` 字段在兼容期改为真实有符号余额，不再截断；套餐余额单独返回，不能与钱包合并成一个误导性的总可用金额。
- 用户列表使用当前页批量钱包摘要，不允许前端再次拉取全部钱包，也不允许逐用户查询套餐。
- 钱包欠费显示红色“欠费”和真实金额；已有套餐仍可用时明确显示“钱包欠费，套餐仍可使用”。
- 套餐购买按钮在欠费时不可用，服务端仍必须重复校验。
- 套餐管理改为选择供应商，模型只读预览并随供应商模型关系自动变化。
- 套餐管理不再提供“是否允许钱包补差”开关；套餐额度不足后的钱包补扣是统一结算规则，不是每个套餐可选的行为。

## 兼容与迁移

1. 先部署只增加结构、不改变行为的迁移。
2. 管理端显示旧套餐待确认的供应商映射；未确认套餐继续使用旧模型范围，不能自动扩大权益。
3. 已确认套餐的新购买记录写供应商快照；已购旧权益由管理员确认后批量生成权益供应商关系。
4. 两台 Frontdoor 都具备新代码后，再通过共享配置切换统一准入、路由和结算；不能只切换其中一部分。
5. 兼容期读取规则优先使用供应商关系；不存在关系时明确标记旧数据并使用旧模型范围，不允许空关系被解释为全部供应商。

## 性能要求

- 不新增顺序执行的跨机房数据库往返。资金查询替换现有错误的套餐查询，计费准入与现有同步候选写入同事务完成。
- 同一请求分批读取服务时，钱包和当前模型套餐只读取一次；后续批次复用本次请求的结果。
- 准入查询不持有资金行锁，不等待其他请求；结算才使用短行锁。
- 对比修改前后的准入耗时、首个响应时间、结算事务耗时和锁等待。OVH 到数据库往返约 25 毫秒，任何新增顺序往返都视为未通过。
- 用户列表查询次数固定，不随页面外用户总数增长。

## 本次复审后的强制修正

- 结算必须找到请求开始时保存的扣费决定。找不到时不得根据当前钱包或套餐猜测扣款；保留该请求的实际费用和 `pending` 结算状态。后台任务在启动时和每五分钟读取已结束但仍待结算的请求，使用同一原子结算逻辑重试；每次失败都按请求 ID 记录错误，且不得修改费用或自行补造扣费决定。
- 请求开始时不再先单独读取扣费决定。首次写入使用一次事务完成扣费决定和请求记录；相同请求重试由同一条写入语句返回已保存决定并校验一致性。
- PostgreSQL 套餐可用额度必须使用固定次数的批量查询，不得按套餐或额度窗口逐条访问数据库。
- 已购旧套餐的供应商范围必须有管理员可执行的补录接口；补录前继续按旧静态模型范围，不得自动扩大权限。
- 请求扣费决定随请求记录保留策略一起清理，只能清理已经完成结算且超过保留期的数据。
- 生产 PostgreSQL 自动测试必须覆盖：缺少扣费决定不扣款、套餐与钱包拆分扣款、重复结算、并发结算和供应商范围。

## 验证方式

- 负钱包加无关、过期或耗尽套餐返回 402；匹配套餐仍有余额时允许。
- 有限钱包恰好为 0 且没有可用套餐时返回 402；只有余额大于 0 时已经开始的最后一批请求，结算后才允许使钱包变成负数。
- 负钱包不能购买、续购或自动续费套餐，已有套餐不失效；余额恢复到 0 后恢复购买。
- 已有生效套餐时不能购买另一套餐；同套餐续费从当前到期时间顺延，创建订单、支付发放和管理员编辑的并发复核都不能产生重叠权益。
- 套餐供应商新增 `gpt-5.6-sol` 后，无需更新套餐模型清单即可用于新请求。
- 同一模型由多个供应商提供时，套餐只能路由到套餐选中的供应商。
- 套餐剩余 2 美元、请求最终费用 8 美元时，套餐扣 2 美元、钱包扣 6 美元；套餐为 0，钱包可以为负。
- 无请求付款决定、套餐供应商越界和重复结算都不能再次扣款；套餐供应商越界不能改成扣钱包。
- 无法估算费用的正常文本、Codex、Claude、Gemini、图片、视频和工具请求仍按实际模型及资金状态判断，不修改正文或能力。
- 管理端用户列表、钱包详情和用户钱包中心显示同一个真实负余额。
- PostgreSQL、MySQL、SQLite 和内存实现的业务语义测试保持一致；生产切换以 PostgreSQL 为准。

## 影响范围

- 数据库迁移、计费和钱包数据仓库、请求候选记录、鉴权、调度、结算、支付回调、套餐发放、管理端套餐页、用户套餐页、用户列表和钱包中心。
- 不改变供应商上游协议，不修改用户请求正文，不增加模型使用限制。
