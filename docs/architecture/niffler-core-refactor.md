# Niffler 核心模型重构设计记录

## 目标

本次重构把旧的 Provider、Endpoint、Key、User Group、价格和错误处理逻辑拆成更清楚的业务边界，后续统一按 Niffler 领域模型维护。

第 1 批只落地安全基础设施：设计文档、共享契约、影子表迁移和只读校验脚本。不接入现有生产请求链路，不改变线上调度、计费、分组、页面或接口行为。

长期目标如下：

- 上游服务只描述供给方，例如 Codex、Claude、OpenAI、Gemini、自定义 OpenAI 兼容接口。
- 上游账号只描述真实可调度凭证，例如 OAuth 账号、API Key、Service Account 或自定义 Header 凭证。
- 产品策略替代旧用户分组，决定用户能用哪些模型、按什么价格销售、是否公开可绑定。
- 用户 Key 只绑定一个产品策略，不再在 Key 自身重复维护可用 Provider、模型和格式规则。
- 价格、计费、调度状态和错误返回规则都有明确字段语义，不再依赖分散的兼容判断。
- 管理后台把新增上游、测试账号、配置图片能力、设置产品策略和价格做成清楚的向导，减少管理员手工理解旧 Provider / Endpoint / Key 的成本。
- 充值、套餐、邀请返利、用量统计和钱包流水使用同一套结算快照，页面必须区分“用量金额”和“真实钱包扣款”。
- 构建、部署和本地开发不能依赖长期堆积的大编译产物；生产发布统一走 CI 镜像，本地只保留必要缓存。

## 非目标

第 1 批不做以下事情：

- 不迁移旧数据。
- 不删除旧字段或旧接口。
- 不修改生产请求链路。
- 不修改管理后台页面。
- 不改变用户实际可用模型、扣费、请求错误内容或账号调度结果。

## 长期工程原则

- 需求字段和代码字段一一对应，避免一个字段同时表达多个业务含义。
- 新旧逻辑不长期双写；新页面切换稳定后，旧接口只读兼容 14 天，然后删除旧读写路径。
- 旧字段可比旧接口多保留一个数据库版本，只读归档；删除前必须有数据校验、回滚说明和线上观测结果。
- 大型重构分批上线，每批都能单独验证、单独回滚，不允许一次切换影响生产运营。
- 数据迁移必须分批、可暂停、可恢复、可重复校验，避免长事务和全表重写。

## 核心模型

### 上游服务

上游服务表示一类供给方，不直接代表某个账号。

典型字段：

- 服务名称：管理员可见名称。
- 服务类型：`codex`、`claude`、`openai`、`gemini`、`openai_compatible`、`anthropic_compatible`、`custom`。
- 默认 API 格式：用于生成默认端点和测试请求。
- 成本倍率：参与上游成本计算。
- 是否启用：停用后不能被产品策略选择，也不能参与调度。
- 默认能力声明：按服务协议声明文本、流式、图片接口、对话内图片工具等能力；OpenAI、Anthropic、Gemini 使用各自协议能力，不能共用 OpenAI Responses 语义。
- 默认测试模板：保存该服务类型的默认测试请求，不要求管理员每次手写请求头和请求体。

### 上游账号

上游账号表示真实可调度凭证，属于一个上游服务。

账号状态统一为：

- 可用：允许参与调度。
- 停用：管理员手动关闭，不参与调度。
- 失效：认证失效或凭证不可用，不参与调度，需要修复凭证后恢复。
- 额度耗尽：官方额度或内部成本窗口耗尽，不参与调度，等额度恢复或管理员处理。
- 冷却中：短时间保护状态，冷却到期后可重新参与调度。

不再把“熔断探测”“测试失败”“配置不完整”作为长期账号状态。手动测试结果、配置检查结果、风险次数和调度保护状态应独立记录。

普通上游 `5xx` 只代表本次请求里的某个上游服务异常，不应直接改变账号状态，也不应让账号进入冷却。调度器应记录本次尝试失败并继续尝试其他账号或服务；只有 `429`、`529`、明确的临时规则、非硬 `403` 或达到阈值的流超时，才允许让账号短时间退出调度。

### 产品策略

产品策略替代旧用户分组，只回答三个问题：

- 用户能用哪些模型。
- 钱包按什么价格销售。
- 这个策略是否允许公开绑定到用户 Key。

产品策略不直接管理上游账号调度。供给侧配置在上游服务和上游账号里维护。

### 上游接入向导

新增上游时后台必须优先使用向导，而不是让管理员先建 Provider、再建 Endpoint、再建 Key。

向导最少分三步：

1. 选择上游类型：Codex OAuth、Claude OAuth、OpenAI API Key、Claude API Key、Gemini Service Account、OpenAI 兼容接口、Anthropic 兼容接口或自定义接口。
2. 填写认证信息：OAuth 走授权流程，API Key 只填密钥和可选账号备注，自定义接口再允许配置 Header。
3. 测试并导入模型：系统自动生成默认端点、默认 API 格式、默认测试请求，测试成功后展示可导入模型和能力。

向导规则：

- 管理员只填必要信息；端点、API 格式、测试请求头和测试请求体由服务类型模板生成。
- 第三方兼容接口按协议手动声明能力。OpenAI 兼容接口可以配置 `/v1/images` 和 OpenAI Responses `image_generation`；Anthropic 兼容接口、Gemini 接口和其他自定义协议只能显示各自协议能力，不能配置 OpenAI Responses 图片工具。
- 如果上游 `/models` 能返回模型，只作为可导入参考；能列出模型不等于模型一定可用，仍要提供按模型测试。
- 上游测试结果只作为最近一次测试记录，不直接变成账号主状态；只有认证明确失效、额度明确耗尽或账号明确封禁，才改变可调度状态。
- 停用服务不能被产品策略选择；已经引用停用服务的旧策略必须在只读对账页列出。

### 图片生成能力

图片能力要按上游服务和端点配置，不让管理员猜“这个上游支不支持”。

能力开关只保留三种：

- 关闭图片能力：不参与图片请求，也不在普通对话里补图片工具。
- 只支持图片接口：只接收明确的 `/v1/images` 或等价图片请求。
- 支持对话内图片工具：普通 OpenAI Responses 对话最终走该上游时，可以补 `image_generation` 工具。

协议边界：

- OpenAI 兼容接口只使用 OpenAI 协议能力，例如 `/v1/images` 和 OpenAI Responses `image_generation` 工具。
- Anthropic 兼容接口不复用 OpenAI 图片工具语义；如果后续支持 Anthropic 图片能力，必须单独定义 Anthropic 协议能力。
- Gemini 接口不复用 OpenAI 图片工具语义；Gemini 图片生成和转换能力必须按 Gemini 协议单独配置。
- Codex / ChatGPT OAuth 账号可以使用 OpenAI Responses 对话内图片工具，但必须通过账号所属服务能力开关启用。

模型规则：

- 用户请求的文本主模型和图片工具模型必须分开记录。
- 对话内生图时，顶层模型是上游执行主模型，图片工具模型写入 `tools[].model`。
- 默认图片工具模型来自模型映射或上游能力配置，不能在代码里长期写死。
- 使用记录必须同时保存用户请求模型、上游执行主模型和图片工具模型。
- 图片费用按结算快照里的实际图片工具模型和图片输出计费规则计算；桥接主模型只作为路由细节保存，不直接决定图片费用。

## 价格和计费

价格字段按以下语义统一：

- 模型基础价格：默认来自官方价格表，可定时同步；历史请求不重算。
- 第三方同步价：第三方接口返回的价格，只作为该上游的参考或可选成本基础。
- 上游成本价格：`基础价格 × 服务成本倍率 × 账号成本倍率`。
- 钱包销售价格：`基础价格 × 产品策略销售倍率`，允许模型级覆盖。
- 套餐消耗：按基础价格消耗，套餐倍率固定为 1。
- 结算快照：每次请求完成时保存当时使用的基础价、销售价、成本价和倍率，后续价格调整不影响历史记录。

计费安全规则：

- 所有请求进入上游前都必须做余额或套餐可用性检查。
- 普通低成本请求只做轻量可用性检查，避免给每次请求增加额外写库压力。
- 长任务、图片、视频和高成本模型必须启用额度预占。
- 额度预占按本次请求的保守上限占用，结束后按真实费用多退少补。
- 预占不足时，请求不能进入上游，避免平台已经产生成本后才发现用户余额或套餐额度不足。
- 预占记录、最终结算记录和回滚记录必须可对账，不能只改钱包余额。
- 钱包按量扣费、套餐额度消耗、平台成本和毛利必须都来自同一次结算快照。
- 请求取消、上游失败、平台本地失败时，未结算的预占必须释放。
- 预占释放必须幂等，同一条预占不能重复返还、重复扣款或重复写流水。
- 进程重启、回调丢失或任务超时后，后台恢复任务按索引分批扫描异常预占，释放或转入人工处理，并写审计记录。
- 最终结算只能绑定一条预占记录；重复回调、客户端重试和后台重试不能产生第二次扣费。

使用和钱包展示口径：

- “用量金额”表示这次请求按计费规则产生的金额，可以包含套餐额度。
- “钱包扣款”只表示真实从钱包余额扣除的金额。
- “套餐扣除”只表示真实从套餐额度扣除的金额。
- 用户侧和管理侧都必须分别展示套餐扣除、钱包扣款和合计用户扣除，不能用单个负数同时表达用量和钱包流水。
- 日汇总必须明确是“用量汇总”还是“钱包流水汇总”；如果展示两者，必须分栏显示。

### 邀请返利

邀请返利纳入结算体系，不再作为支付回调里的附带逻辑分散处理。

返利规则：

- 返利触发点只认支付成功后的有效入账事件，不认未支付订单、取消订单或失败回调。
- 同一支付订单只能触发一次返利，必须有幂等键。
- 返利金额、邀请人、被邀请人、订单号、规则快照和发放状态必须写入返利流水。
- 返利入账失败不能影响用户本次充值入账，但必须进入待重试状态并在管理后台可见。
- 管理后台要能按用户、订单、邀请关系查询为什么发放或为什么未发放。
- 管理后台必须提供返利规则配置入口，至少支持启用状态、返利比例或固定金额、适用订单范围、返利上限和生效时间。
- 管理后台必须支持失败返利重试、手动补发、手动取消和操作审计；所有人工操作都必须保留原因和操作者。

页面要求：

- 支付订单详情展示返利状态。
- 用户详情展示邀请关系、累计返利、待重试返利。
- 返利规则变更不影响历史订单，历史订单按当时规则快照对账。

## 调度和请求记录

长期请求链路应按以下顺序执行：

1. 校验用户 Key 状态和产品策略。
2. 校验模型是否在产品策略里可用。
3. 找到支持该模型且启用的上游服务。
4. 找到服务下状态为可用的上游账号。
5. 按账号调度策略选择实际账号。
6. 记录每一次尝试的服务、账号、状态、跳过原因、上游状态码和耗时。
7. 结算时写入价格快照和扣费快照。

请求记录列表不能裸露展示 `unknown`。底层兼容字段可以临时保留 `unknown` 或 `pending`，但管理后台必须显示业务原因，例如“未进入供应商”“平台拦截”或“号池未选出账号”。已经请求到上游时，必须记录并展示实际服务和账号。

## 错误返回设置

错误返回设置分为平台级和上游级。

平台级用于 Niffler 本地拦截错误，例如：

- 用户 Key 无效。
- 用户 Key 暂停。
- 余额不足。
- 套餐额度不足。
- 模型不在产品策略。
- 没有可用上游账号。
- 频率限制。
- 平台维护。

上游级用于已经请求到上游后的错误，例如：

- 上游返回风控关键词。
- 第三方上游在错误里加入客服信息或营销广告。
- 官方上游错误需要改成用户更容易理解的说明。
- 默认上游错误文案。

上游级处理顺序固定为：

1. 风控关键词。
2. 广告或客服内容替换。
3. 状态码文案。
4. 默认上游错误文案。

风控关键词命中后可以触发账号保护动作。动作只保留三种：只记录、暂停调度、标记人工处理。暂停时长只保留四种：10 分钟、1 小时、24 小时、手动恢复。

原始上游响应明文只保存给管理员审计和请求记录排查使用，普通用户和用户侧接口不能看到原始全文，除非规则选择追加说明。

## 性能和并发

- 调度读路径必须优先使用缓存和预计算状态，不能在每次请求里做多表重查询。
- 账号状态、额度窗口和风险统计需要可增量更新。
- 管理后台统计查询必须分页、限制时间范围并走索引。
- Postgres 日统计后台聚合必须低压运行：聚合事务内关闭查询并行；补跑多个 UTC 日期时，每个成功日期之间短暂停顿，不能用紧密循环连续压数据库。
- 迁移脚本不得做无条件全表更新；需要数据迁移时必须分批提交，并输出进度。
- 只读校验脚本默认不写数据库，线上执行时必须有超时和结果摘要。
- 计费预占和释放事件必须有幂等键；数据库层必须拦住缺少幂等键的事件，不能只依赖接口校验。
- 邀请返利百分比统一用 `0` 到 `1` 的小数表示；数据库层必须拒绝大于 `1` 的百分比规则。
- 生产发布只使用 CI 构建产物，不在生产服务器编译 Rust、前端或 Docker 镜像。
- 本地构建目录、Docker 缓存和临时镜像需要有清理脚本和安全阈值；清理脚本默认 dry-run，只删构建产物和缓存，不删源码、数据库和配置。
- 生产发布必须显式指定 CI run 或提交号，避免误部署旧产物。部署脚本可以保留“最新成功产物”能力，但只能用于本地验证或临时排查，不能作为生产发布默认流程。

## 分批上线计划

### 第 1 批：影子结构

新增设计文档、共享契约、影子表迁移和只读校验脚本。不接入运行时。

本批同时新增安全清理脚本和发布约束文档。清理脚本必须有路径白名单、dry-run 输出和危险路径拦截，只允许清理本地构建产物、Docker 悬空缓存和临时 CI 包。

验收标准：

- 新契约类型能独立编译和测试。
- 迁移只新增影子表和索引，不修改旧表。
- 影子表必须进入逻辑 schema；Postgres 空库 bootstrap 快照必须包含快照截止版本内的影子表，不能只依赖增量迁移。
- 校验脚本只读，能输出旧数据迁移风险报告。
- 清理脚本默认只预览不删除，显式确认后才执行，并且不会触碰源码、数据库和配置文件。
- 发布文档明确生产必须指定 Git 提交号或 CI run。

### 第 2 批：后台只读视图

新增 Niffler 模型只读 API 和管理后台只读页面，对照旧 Provider、Key、User Group、价格和请求记录，不允许写入。

本批只做“看清旧数据能否映射到新模型”，不做迁移和修复。后台负责统一聚合旧 Provider、Key、用户分组、模型价格和最近请求记录，前端只展示聚合结果，不在浏览器里拼接旧表含义。

旧分组来源必须使用现有用户后台实际读写的 `user_groups`。历史 `routing_groups` 不再作为产品策略对账来源，避免页面显示“产品策略为 0”但实际用户 Key 仍绑定用户分组。

只读 API：

- `GET /api/admin/niffler-core/readiness?recent_days=7`
- `recent_days` 默认 7 天，允许 1 到 90 天。
- 返回影子结构状态、旧数据映射摘要、停用 Provider 引用、Key 自身残留限制、分组策略缺口、价格缺口、最近异常 `unknown/pending` 请求记录和路由跳过原因。正常正在进行的 `pending` / `streaming` 请求不算迁移阻断；用户 Key 并发上限、产品策略拒绝、余额不足、没有可用上游服务这类平台在选择上游前按规则拒绝的请求，不算迁移阻断；只有已经完成仍未结算，或创建超过 30 分钟仍未结算的请求才进入 readiness 异常列表。
- 每类问题必须由后端返回管理员可读的原因、影响和建议处理方向；前端只展示聚合结果，不在浏览器里解释旧字段。
- Provider、上游账号和用户分组必须优先展示后台可见名称。上游账号优先展示邮箱和手机号；没有账号标识时再展示 Key 名称，避免只显示内部 ID。
- 路由跳过原因必须同时返回原始代码和中文说明，例如 `pool_cooldown` 显示为“账号仍在冷却，调度器不会选择它”。
- 时间字段统一按秒级 Unix 时间返回，字段名必须写成 `*_unix_secs`，不能把秒级时间命名为 `*_unix_ms`。
- 查询必须限制数量。最近请求记录默认只取 50 条问题样本，避免后台页面触发大范围扫描。
- API 只读取旧表和影子表元信息，不写 `niffler_*`，不修改旧 Provider、Key、分组、价格或请求记录。

管理后台新增独立页面“核心对账”。页面顶部必须明确标注“只读检查，不会修改数据”，并把风险按业务含义展示：

- 旧 Provider 能否映射为上游服务。
- 旧 Key 能否映射为上游账号。
- 用户分组能否映射为产品策略。
- 哪些停用 Provider 仍被分组引用。
- 哪些用户 Key 或 Provider Key 仍有自身限制。
- 哪些模型或 Provider 模型缺价格。
- 最近请求记录里哪些因为没有实际上游账号、结算卡住或旧兼容字段导致显示 `unknown/pending`；正常进行中的请求、以及平台在选择上游前按规则拒绝的请求不展示为迁移异常。
- 最近路由尝试里哪些账号或服务被跳过，以及这些跳过原因是否属于冷却、停用、额度耗尽、成本限制、产品策略限制或格式不匹配。

验收标准：

- 新旧视图数量可对账。
- `unknown` 来源能在只读视图里定位。
- 停用 Provider 引用、Key 独立限制、分组策略缺口、价格缺口、异常请求和路由跳过原因都能在页面上看到“原因、影响、建议处理方向”。
- 不影响旧页面操作。

### 第 3 批：管理写入切换

新增上游服务、上游账号、产品策略、错误返回设置的写入入口。旧页面不一刀切只读：已迁移对象在旧页面只读或提示去新页面修改；未迁移对象仍允许旧页面写入，直到该对象完成迁移和对账。

第 3 批分小片上线，第一片只新增“上游接入”写入入口：

- 只写 `niffler_upstream_services`、`niffler_upstream_accounts` 和 `niffler_upstream_service_capabilities`。
- 不读取这些新表参与现有请求调度、计费、结算、账号状态判断或用户可见模型列表。
- 不迁移旧 Provider、Endpoint、Key，也不修改旧表。
- 不提供删除和批量迁移，避免管理员误以为新页面已经接管线上流量。
- 页面必须明确提示“写入新模型，不影响当前线上调度”。

第 3 批第二片新增“产品策略”写入入口：

- 只写 `niffler_product_plans` 和 `niffler_product_plan_models`。
- 产品策略只登记名称、公开状态、启用状态、钱包销售倍率和说明。
- 产品策略模型只登记模型名称、是否启用和模型级销售倍率覆盖。
- 不把新产品策略绑定到用户 Key，不读取新产品策略参与当前模型权限、调度、计费、套餐或钱包扣费。
- 不迁移旧 `user_groups`，不修改旧分组、旧 Key 或旧 Provider 模型价格。
- 页面必须明确提示“产品策略仍是新模型配置，不影响当前用户可用模型和价格”。

第 3 批第三片新增“错误返回设置”写入入口：

- 只写 `niffler_error_return_settings`。
- 平台级规则由管理员选择平台错误原因，系统自动写入内部错误代码和对应状态码；页面不要求管理员手填 401、403、429 这类 HTTP 状态码。
- 上游级规则按处理类型展示字段：风险关键词和广告替换只填关键词，状态码文案只填上游状态码，默认上游文案不填关键词和状态码。
- 平台级规则不能触发上游账号保护；上游级只有风险关键词可以触发账号保护，“暂停调度”必须选择固定暂停时长。
- 不读取新错误返回设置参与当前用户请求，不修改现有错误返回内容、账号状态、风控统计、请求记录或调度结果。
- 页面必须明确提示“错误文案规则仍是新模型配置，不影响当前线上错误返回”。

本批同时明确管理后台页面边界，避免继续把旧 Provider、分组、Key、灰度和对账概念混在同一页：

- 上游接入页只负责供给侧接入：新增上游、登记账号、声明服务能力、测试上游和导入模型。该页不展示产品策略、用户 Key 绑定、灰度、计费预占、返利、结算快照、路由观察或错误文案规则。
- 产品策略页只负责销售侧配置：可售模型、钱包销售倍率、模型级倍率覆盖、公开状态和适用密钥。页面文案使用“适用密钥”，不使用“Key 绑定”“影子策略”这类工程迁移词。
- 错误提示页只负责错误返回规则：平台错误、上游错误、风险关键词、用户文案和账号保护动作。上游接入页只在服务详情里给出入口提示，不直接编辑错误规则。
- 迁移与对账页只负责内部迁移观察：灰度开关、预占、结算快照、路由尝试、一致性看板和稳定观察。该页必须明确是迁移工具，不作为管理员日常接入配置入口。
- 新增上游服务时自动生成默认端点、默认 API 格式和默认测试请求。
- OAuth 账号、API Key 账号和自定义 Header 账号使用同一个账号模型，但前端按认证方式展示不同表单。
- 第三方兼容接口允许手动声明图片能力和对话内图片工具能力。
- 模型导入后，管理员只在产品策略里设置销售倍率或模型售价覆盖，不再在旧分组里重复维护 Provider 模型价格。
- 页面按钮必须使用短动作文案，例如“新增上游”“添加账号”“保存能力”“添加模型”“添加密钥”“改策略”“移除”。解释性长句放在标题旁说明或帮助提示里，不放在按钮上。

接入向导先分片落地。第一片只做“接入类型模板”：管理员选择 Codex OAuth、Claude OAuth、OpenAI API Key、Claude API Key、Gemini Service Account、OpenAI 兼容接口、Anthropic 兼容接口或自定义接口后，页面自动预填服务类型、协议、默认 API 格式、默认账号认证方式和可配置能力。高级字段仍可调整，但默认流程不再要求管理员理解旧 Provider、Endpoint、API 格式、测试请求头和测试请求体。第一片不调用上游测试、不导入模型、不保存真实凭证、不接入现有调度或计费。

第二片做“产品策略模型选择和价格预览”：新增可售模型时优先从现有全局模型选择，页面展示模型基础价格、策略默认销售倍率、模型级销售倍率覆盖和钱包销售价格预览。该预览只帮助管理员理解价格关系，保存时仍只写模型名称、启用状态和销售倍率覆盖；不修改全局模型基础价、不迁移旧分组价格、不接入当前计费链路。

第三片做“账号登记体验和测试状态展示”：新增上游账号时按认证方式展示管理员需要填写的账号标识，OAuth 账号强调邮箱或手机号，API Key 账号强调账号备注和可选联系信息，自定义 Header / Service Account 账号强调当前只登记身份不保存凭证。账号列表展示认证方式、成本倍率、优先级、最近测试结果、冷却时间和测试错误。该片仍不保存真实凭证、不调用上游测试、不改变账号调度状态、不接入当前调度或计费链路。

第四片做“图片能力配置展示”：服务能力从 `niffler_upstream_service_capabilities` 读取并展示，管理员可以按协议调整图片接口和 OpenAI Responses 对话内生图工具能力。页面提供本地配置检查，只确认协议和能力没有混用，不请求真实上游、不保存真实凭证、不测试实际生图、不改变当前调度或计费链路。真实图片能力测试要等凭证保存、测试请求模板和图片测试执行器接入后再启用。

第五片做“产品策略绑定 Key 影子配置”：新增独立的 `niffler_api_key_product_plan_bindings` 表，记录一把用户 Key 当前绑定的一个产品策略。该绑定不复用旧 `api_keys.group_id`，不修改旧用户分组，不接入当前模型权限、调度、计费、套餐或钱包扣费。管理后台只允许把一把 Key 绑定到一个启用的产品策略；重新选择产品策略时更新同一条绑定记录，避免一把 Key 同时出现多个产品策略。后台提供全量读取和按策略读取两个只读入口，管理页一次加载当前绑定关系，避免为了展示 Key 当前策略反复请求每个策略。

验收标准：

- 上游接入页只加载和上游服务、账号、能力相关的数据，打开页面时不请求产品策略、用户 Key、灰度、结算、返利、路由观察或错误规则接口。
- 新页面能完成新增服务、账号、产品策略、价格和错误文案配置，但这些配置必须分布在对应页面，不堆在上游接入页。
- 新增 OpenAI 兼容接口时，不需要手写测试请求头和请求体也能完成基础测试。
- 第三方图片能力能在后台看见、配置和测试。
- OpenAI、Anthropic、Gemini 和自定义协议的能力配置不会互相显示或混用。
- 停用服务不能被产品策略选择。
- 用户 Key 只能绑定一个产品策略。
- 日常配置页不显示“影子策略”“灰度登记”“预占干跑”这类迁移期词汇；迁移与对账页必须明确标识为内部迁移工具。

### 第 4 批：运行时灰度

按管理开关启用新调度和新结算快照，先灰度内部 Key，再扩大到指定产品策略。

第 4 批第一片先做“运行时灰度开关影子配置”：新增 `niffler_runtime_rollout_settings` 表，只登记某个用户 Key 或产品策略准备启用哪些新链路。支持的开关包括新调度、新结算快照、错误文案规则、额度预占和返利流水。该表不接入当前请求链路，旧调度、旧计费、旧结算、旧错误返回和返利逻辑都不读取这张表；后台页面必须明确提示“保存后不会立刻影响线上请求”。同一个灰度对象只保留一条设置，重复保存时更新原记录，避免同一 Key 或产品策略出现多份互相冲突的开关。

第 4 批第二片做“灰度决策预览”：后端新增只读预览接口，按一把用户 Key 当前影子绑定的产品策略和灰度开关，计算后续运行时会使用的最终开关结果。Key 级灰度开关优先于产品策略级灰度开关；如果 Key 没有绑定影子产品策略，或对应产品策略没有启用的灰度开关，预览结果必须明确说明不会启用新链路。该接口只读取 `niffler_api_key_product_plan_bindings`、`niffler_product_plans` 和 `niffler_runtime_rollout_settings`，不写数据库，不接入请求链路，不改变旧调度、旧计费、旧结算、旧错误返回和返利逻辑。管理后台在灰度开关卡片里展示“最终预览”和命中来源，避免管理员只看到两张影子表，却不知道某把 Key 后续实际会按哪条配置判断。

第 4 批第三片做“预占和返利流水只读对账”：后端新增只读列表接口，分页读取 `niffler_billing_reservations` 和 `niffler_referral_reward_ledger`。该片只用于管理员确认影子预占、释放、结算和返利流水的数据形状，不创建预占、不释放预占、不发放返利、不重试返利、不接入支付回调、不接入请求扣费链路。管理后台在运行时灰度卡片后展示两个只读表格，支持按状态筛选，并明确提示“当前为空是正常的，只有后续启用新链路写入后才会出现数据”。本片完成后，下一片再做内部 Key 的运行时读开关和最小可对账写入。

第 4 批第四片做“运行时读开关和影子路由尝试写入”：请求结束后的执行报告会读取当前用户 Key 的灰度开关，Key 级设置优先，Key 未配置时读取影子产品策略绑定和产品策略级设置。只有最终命中 `enable_new_routing` 的请求，才会把旧运行时已实际使用的 provider、账号、模型、上游状态码、耗时和状态写入 `niffler_route_attempts`。本片不改变旧调度选择，不读取新上游服务参与调度，不写预占，不写结算快照，不扣钱包，不消耗套餐，不改变错误返回。灰度决策需要短缓存，避免每个请求结束都查询影子配置表；缓存只影响是否写影子对账记录，不影响请求结果。影子写入失败只能记日志，不能影响用户请求或原有用量上报。

第 4 批第五片做“影子路由尝试只读对账”：后端新增分页只读列表接口，读取 `niffler_route_attempts` 里的影子尝试记录，支持按请求 ID、上游服务、上游账号和状态筛选。该接口默认按创建时间倒序返回最近记录，单页数量必须限制在 1 到 100，避免后台页面触发大范围扫描。管理后台在运行时灰度区域展示这些影子记录，让管理员确认灰度请求实际写入了哪个服务、账号、模型、上游状态码、耗时和状态。本片不创建影子记录，不修改灰度开关，不接入新调度，不参与计费、结算、扣钱包、套餐消耗或错误返回。

第 4 批第六片做“结算快照影子写入和只读对账”：请求完成后读取旧结算链路已经算出的权威结果，只有命中 `enable_settlement_snapshot` 的用户 Key 才写入 `niffler_settlement_snapshots`。该片不重新计算价格，不改变钱包扣费，不消耗套餐，不创建预占，不改变使用记录展示；只把旧链路已经产生的销售金额、套餐金额、上游成本、毛利、模型、上游服务和账号复制成新结算快照，方便对账。影子写入必须同时拿到旧定价快照和旧扣费分解，缺少钱包/套餐分解时跳过，不能用总销售价推测钱包或套餐扣费。写入必须按 `request_id` 幂等，失败只能记日志，不能影响用户请求。后台新增结算快照只读表，支持按请求 ID、用户 Key、产品策略筛选，并按创建时间倒序分页，单页限制 1 到 100。

第 4 批第七片做“预占干跑估算”：新增独立的 `niffler_billing_reservation_dry_runs` 表记录预占估算结果，不写 `niffler_billing_reservations`，避免把没有真实冻结余额的记录伪装成预占。只有命中 `enable_billing_reservation` 的用户 Key 才在请求完成后写入一条干跑记录，字段包括请求 ID、用户、Key、产品策略、模型、估算预占金额、旧链路最终扣费、差额、估算来源和状态。该片不在请求开始前拦截余额，不冻结钱包，不释放余额，不影响套餐，不改变错误返回；用途是先确认“旧结算快照里的应收金额”和“最终钱包/套餐扣费”是否能稳定对账，为下一片请求开始前真实预占做准备。估算预占金额优先取旧结算快照里的 `user_total_cost_usd` 或 `total_cost`，旧链路最终扣费取 `charge_breakdown_snapshot.wallet_debit_usd + charge_breakdown_snapshot.package_debit_usd`；两边都缺失时跳过，不能用上游成本或毛利反推。后台新增干跑对账表，默认只看最近记录，支持按状态和请求 ID 筛选，单页限制 1 到 100。

第 4 批第八片做“真实预占最小闭环”：只允许对内部测试 Key 启用，且必须命中 Key 级 `enable_billing_reservation`；产品策略级开关在本片只继续产生干跑对账，不允许触发真实预占。请求通过本地鉴权、模型权限、余额粗检查和频率限制后，在进入上游前复用现有请求前成本上限估算，计算本次需要锁定的钱包金额。余额判断必须扣除同一用户或同一独立 Key 的 active 预占金额；余额不足时直接返回平台余额错误，不请求上游，不创建 active 预占。余额足够时创建 `niffler_billing_reservations` active 记录和 reserved 事件，表示这笔可用额度已被本次请求锁定。

第八片的“冻结钱包可用余额”不直接减少 `wallets.balance` 或 `wallets.gift_balance`，也不写钱包交易。原因是旧结算仍是实际扣费来源，如果预占阶段先扣钱包，旧结算会再次扣费。该片采用“active 预占记录参与可用余额计算”的方式冻结额度：请求期间新的预占检查会把 active 预占金额视为不可用；请求完成后，成功请求按旧结算快照转为 `settled`，失败、取消、超时、本地异常或没有实际扣费的请求转为 `released`。为避免同一用户并发请求同时通过余额判断，真实预占的 active 汇总检查和 active 记录创建必须在同一进程内按用户串行执行。旧钱包扣费口径、套餐消耗、用户账单展示和使用记录仍以旧结算为准；预占表只作为内部测试 Key 的请求前拦截和对账证据。

第八片不替换旧钱包扣费链路，不面向公开产品策略启用，不修改套餐实际消耗，不让新 `niffler_*` 表参与普通用户的调度、计费、结算、模型列表或错误返回。进程重启后，后台任务只扫描过期 active 预占，能确认没有结算结果的转为 `expired`，数据矛盾或无法判断的转为 `manual_review`，并写对应事件；该扫描必须分页处理，不能对生产库做无界全表扫描。当前后台任务每 60 秒执行一轮，每轮最多处理 10 批，每批最多 100 条过期 active 预占；达到上限时等待下一轮继续处理。

第 4 批第九片做“错误返回规则灰度接入”：只有命中 `enable_error_return_rules` 的请求才读取新错误返回设置。平台级错误只处理已确定用户 Key 后产生的余额不足、模型不可用、速率限制等平台错误；上游级错误只处理已经请求到上游后的状态码和关键词匹配。上游级规则支持替换返回文案，并在匹配风险关键词时记录账号风险次数；账号风险动作只允许暂停调度固定时长或标记人工处理，不直接删除账号。该片不改变未灰度 Key 的错误返回，不改变旧账号状态字段，不把风险统计混进熔断逻辑。

第九片的运行时接入只覆盖能确定用户 Key 的请求。无效 API Key 这类在鉴权前无法确定 Key 的平台错误继续使用旧返回；已确定 Key 的余额不足、模型不可用、频率限制和本地拦截错误，可以按平台级规则替换用户文案。上游级规则只在请求已经选中上游服务和账号、并拿到上游失败响应后生效；命中规则时只改用户看到的响应内容，原始上游响应继续保存在请求记录上下文里供管理员排查。风险关键词命中后写入 `niffler_account_risk_events`，记录上游账号、用户 Key、请求、模型、规则和动作；本片不直接修改旧 Provider Key 状态，也不让风险事件参与旧调度。

第 4 批第十片做“返利流水影子写入”：支付成功后，旧返利逻辑仍先按原规则创建和发放 `referral_rewards`；只有这次订单确实产生了旧返利，且能从支付订单所属用户的用户 Key 解析出唯一命中的 `enable_referral_ledger` 灰度范围，才写入 `niffler_referral_reward_ledger` pending 记录。解析规则是：Key 级灰度优先；如果用户只有一个启用返利流水的 Key 级设置，按该 Key 写入；否则再看这些 Key 绑定的产品策略，如果只有一个启用返利流水的产品策略，按该产品策略写入；没有命中或命中多个范围都跳过，不能随便选一把 Key 或一个策略。该片不发放钱包余额，不修改旧返利逻辑，不重试失败返利；只把旧返利结果汇总成同一支付订单最多一条新返利流水，并能在后台看到旧规则快照、灰度命中来源、邀请人、被邀请人、订单、金额和当前状态。旧返利逻辑仍是实际发放来源。

第 4 批第十一片做“返利发放最小闭环”：命中 `enable_referral_ledger` 的订单改由新返利流水发放；没有命中灰度的订单继续走旧返利逻辑。新链路先创建订单级 `niffler_referral_reward_ledger`，再在同一发放事务里锁定邀请人钱包、写钱包交易、把流水改为 `paid` 并写 `paid` 事件。为保留旧后台统计、退款冲回和对账依据，旧 `referral_rewards` 仍记录每条返利明细，但命中灰度时初始状态必须是 `ledger_pending`，不允许进入旧的 pending/failed 重试发放队列；新账本发放成功后再把这些旧明细同步为 `applied` 并记录同一个钱包交易 ID。新账本发放失败时，流水改为 `failed`，旧明细改为 `ledger_failed`，只允许走新账本的重试/取消入口，不能让旧返利重试再次发钱。发放必须按订单和幂等键保证只执行一次；成功后写钱包交易和 paid 状态；失败后写 failed 状态、失败原因和可重试次数；管理员可以手动重试、取消或补发，所有动作写审计事件。该片上线后，同一灰度范围内旧返利发放必须关闭，不能双发。

第 4 批第十二片做“灰度范围扩大和一致性看板”：把新结算快照、真实预占、错误返回规则和返利流水从内部 Key 扩大到指定产品策略。产品策略级 `enable_billing_reservation` 命中后允许创建真实预占，预占金额、余额占用、完成释放和结算仍沿用第八片的规则；Key 级灰度仍优先于产品策略级灰度。后台新增只读一致性看板，按请求 ID 汇总旧 `usage`、旧 `usage_settlement_snapshots`、新 `niffler_settlement_snapshots`、新 `niffler_billing_reservations`、套餐 `entitlement_usage_ledgers` 和影子路由尝试，计算钱包扣费误差、套餐扣费误差、合计误差、预占是否完成、结算快照是否存在。查询必须从新结算快照按创建时间分页，支持按请求 ID、用户、Key、产品策略筛选，单页限制 1 到 100；接口不做精确总数统计，只返回当前页，避免后台看板默认访问时触发全表统计。返利流水仍按订单独立展示，不强行塞进请求级看板。只有看板里目标产品策略最近请求的合计误差为 0，且没有缺失旧使用记录、缺失新结算快照、未完成预占或人工处理状态，才允许继续扩大灰度。该片仍保留旧链路回滚能力，不删除旧字段和旧页面。

第十二片非目标：

- 不把新上游服务接入旧调度。
- 不把新产品策略接入旧用户模型列表。
- 不删除旧分组、旧使用记录、旧结算字段或旧页面。
- 不用后台看板主动修账，发现误差只展示原因，人工处理另走后续任务。

第十二片验证方式：

- 产品策略级 `enable_billing_reservation` 的测试 Key 会创建真实预占，并在请求完成后按旧结算结果变为 `settled` 或 `released`。
- Key 级灰度仍覆盖产品策略级灰度。
- 一致性看板只读接口在空数据、缺失旧使用记录、金额一致和金额不一致四种情况下都返回明确状态。
- 前端页面展示请求级对账结果，不提供修改按钮。

验收标准：

- 新旧调度结果可对账。
- 钱包扣费、套餐消耗、上游成本和请求记录一致。
- 错误返回文案符合平台级和上游级规则。
- 预占不足的请求不会进入上游。
- 请求取消、上游失败、任务超时和进程重启后的异常预占能正确释放或进入人工处理。
- 钱包流水、套餐扣除和用量汇总页面口径一致。
- 邀请返利对同一支付订单只发放一次，失败可重试。

### 第 5 批：旧逻辑下线

新链路稳定后，旧接口只读兼容 14 天。满足删除条件后移除旧写入逻辑、旧页面和旧字段读路径。

第 5 批前置条件：

- 目标产品策略已经 100% 命中新调度、新结算快照、真实预占、错误返回规则和返利流水。
- 一致性看板连续返回最近请求无金额误差、无缺失旧使用记录、无缺失新结算快照、无未完成预占、无人工处理状态。
- 使用记录中实际请求到上游的记录都能显示明确上游服务和上游账号，不再依赖旧兼容字段补显示。
- 管理后台已经能用新页面完成上游服务、上游账号、产品策略、模型价格、错误文案和返利处理。
- 生产最近一次发布来自 CI artifact，且有可回滚的上一版镜像、最近数据库备份和回滚演练记录。

第 5 批拆分为以下小片，必须按顺序推进：

1. 第 5 批第一片做“旧依赖只读稽核”。新增只读看板，分页检查旧 `api_keys.allowed_providers`、`allowed_models`、`allowed_api_formats`、旧用户分组、旧 Provider、旧 Provider 模型价格、旧页面写入口和旧运行时读路径是否仍有真实访问。该片不改写旧数据、不删除字段、不改变请求链路；查询必须从索引字段分页，不做无界全表统计。
2. 第 5 批第二片做“旧写入口冻结”。把已迁移对象的旧 Provider、旧 User Group、旧模型价格和旧 API Key 限制入口改为只读或跳转到新页面；未迁移对象仍按旧逻辑处理，并在稽核看板中明确列出。冻结动作必须写审计日志，错误提示必须说明应该去哪个新页面修改。
3. 第 5 批第三片做“运行时权威读源切换”。对已迁移产品策略，运行时只读取新上游服务、上游账号、产品策略和价格快照；旧字段只用于未迁移对象。已迁移对象缺少新配置时直接返回明确的平台配置错误，不能再静默回退到旧字段。
4. 第 5 批第四片做“旧接口只读兼容”。旧管理接口只返回新权威数据的只读投影，旧页面只展示或提示迁移后的新入口，不再保留旧写入分支。该片开始记为旧接口只读兼容期的 T0。
5. 第 5 批第五片做“14 天稳定观察”。从 T0 起连续 14 天自动记录一致性看板、旧接口访问审计、请求 `unknown` 统计、预占异常、返利异常和回滚演练状态。出现 P0/P1 计费或调度事故、金额误差、上游服务或账号 `unknown`、旧写接口被真实调用、回滚演练失败，T0 清零重算。
6. 第 5 批第六片做“删除旧写逻辑和旧页面”。只有 14 天稳定观察通过后，移除旧 Provider/User Group/Provider 模型价格写入代码和旧页面入口；保留旧字段只读查询能力用于回滚和历史排查。该片仍不删除数据库字段。
7. 第 5 批第七片做“旧字段读路径删除”。第六片上线后再观察 30 天；如果没有回滚、没有旧字段读取审计、没有生产排障依赖旧字段，就删除运行时和后台对旧字段的读路径。旧字段仍保留在数据库中，只作为最终删除前的备份数据。
8. 第 5 批第八片做“旧字段和旧表最终删除”。第七片上线后满 14 天，且确认代码搜索、运行时审计和后台访问都不再读取旧字段，才在维护窗口删除旧字段或旧表。删除前必须有数据库备份、回滚说明和锁表影响评估；删除后不再承诺字段级回滚，只能通过备份恢复。

稳定标准：

- 连续 14 天无 P0/P1 计费或调度事故。
- 请求记录中实际请求到上游的记录不再出现 `unknown` 服务或账号。
- 用户 Key、产品策略、上游服务和上游账号的数据对账误差为 0。
- 管理员已不再使用旧 Provider/User Group 写入口。
- 回滚演练通过，且有最近一次数据备份。
- 本地和生产发布流程都不依赖生产服务器编译；部署记录能追溯到 Git 提交号和 CI run。

旧逻辑保留时间：

- 旧写入口：T0 后只读兼容 14 天；稳定观察通过后删除旧写入代码和旧页面入口。
- 旧运行时读路径：旧写入口删除后再保留 30 天；没有回滚和读取审计后删除代码读路径。
- 旧数据库字段和旧表：旧读路径删除后再保留 14 天；维护窗口内最终删除，不永久保留。

删除条件：

- 代码搜索确认运行时、后台接口、前端页面和脚本都不再引用待删除旧字段或旧接口。
- 生产审计确认 14 天内没有旧写接口调用，30 天内没有旧字段读路径命中。
- 一致性看板最近 14 天无金额误差、无未完成预占、无缺失结算快照、无人工处理状态。
- 请求记录最近 14 天无实际上游服务或账号 `unknown`。
- 最近一次 CI 全绿，最新发布来自 CI artifact，生产健康检查和核心只读接口验证通过。
- 已完成数据库备份、回滚演练和锁表影响评估。

第 5 批第一片接口：

- `GET /api/admin/niffler-core/legacy-dependency-audit?offset=0&limit=50`
- `offset` 默认 0；`limit` 限制在 1 到 100，接口用 `limit + 1` 判断是否还有下一页，不做精确总数统计。
- 只读返回独立用户 Key 的旧限制字段、旧用户分组策略字段、Provider Key 旧限制字段、旧 Provider 模型价格依赖、旧写入口清单和旧运行时读路径清单。
- 独立用户 Key 使用现有分页导出能力读取；普通用户 Key 目前没有跨用户分页仓储，本片不能为了稽核新增无界扫描，只在报告里明确“仍需访问审计确认”。
- 旧写入口和旧运行时读路径先按代码中仍存在的入口返回静态清单；第二片冻结旧写入口前，再接入真实访问审计。
- 接口不写 `niffler_*`，不修改旧 Provider、Key、分组、价格、请求记录或灰度开关。

第 5 批第二片冻结规则：

- 本片只上线冻结机制，不批量修改旧数据，不删除旧字段，不切换运行时读源。
- 只有同 ID 的新对象存在时，才判定旧对象已经迁移：旧 Provider ID 对应 `niffler_upstream_services.id`；旧 Provider Key ID 对应 `niffler_upstream_accounts.id`；旧 User Group ID 对应 `niffler_product_plans.id`；旧用户 Key ID 对应 `niffler_api_key_product_plan_bindings.api_key_id`。
- 生产新 Niffler core 表为空时，本片默认不冻结任何现有旧配置，旧入口仍按旧逻辑处理。
- 已迁移旧 Provider 的更新、删除、端点维护和模型价格维护入口返回 `409 Conflict`，提示到 Niffler core 上游服务页面修改。
- 已迁移旧 Provider Key 的更新、删除、清除失效标记、重置周期统计、池内冷却清除、成本窗口重置、号池批量导入、号池批量操作和清理异常账号入口返回 `409 Conflict`，提示到 Niffler core 上游账号页面修改。
- 已迁移旧 User Group 的更新、删除入口返回 `409 Conflict`，提示到 Niffler core 产品策略页面修改；创建新旧分组和成员维护本片暂不冻结。
- 已绑定新产品策略的用户 Key，旧页面提交 `group_id` 时返回 `409 Conflict`，提示到 Niffler core 用户 Key 产品策略绑定页面修改；只改 Key 名称、限速、并发和功能开关仍允许。
- 系统导入、后台 OAuth 刷新、配额同步、自动探测和固定 Provider 模板维护本片不冻结；这些路径在第三片运行时读源切换前仍承担维护和回滚职责，必须等新读源接管后再改为只读投影或新表写入。
- 冻结响应必须通过 `attach_admin_audit_response` 写审计，事件名为 `niffler_legacy_write_frozen`，动作名为 `freeze_legacy_write`。

旧用户分组 Provider 写入收敛规则：

- 历史用户分组中已经保存的停用 Provider 不由本片自动删除；这些引用继续只读展示，并由 readiness 报告提示管理员清理。
- 新建或更新旧用户分组时，如果 `allowed_providers_mode` 为 `specific`，提交的 `allowed_providers` 必须全部能在 Provider catalog 中找到，且 Provider 必须处于启用状态。
- Provider catalog 读源不可用时，旧用户分组不能保存指定 Provider 限制，接口必须返回明确错误，避免在无法校验供给侧状态时写入新的错误配置。
- 管理后台旧用户分组页面只能提供启用中的 Provider 作为可选项；停用 Provider 不再进入新保存请求。
- 稽核看板继续只读、分页和限量；旧写入口清单改为说明已经接入冻结机制，不做无界统计。

Provider Key 残留判断规则：

- `api_formats`、`auth_type_by_format` 和 `allow_auth_channel_mismatch_formats` 表示账号协议和认证能力，旧运行时、账号测试、OAuth 导入和模型获取仍需要读取；readiness 不把这些字段当成 Key 自身旧限制。
- `allowed_models` 在 `auto_fetch_models = true` 时表示旧 Key 上自动同步出来的账号模型清单，不是管理员手动白名单；readiness 必须标成“自动同步模型清单”，并提示迁到 `niffler_account_model_capabilities`。
- 自动同步模型清单的 readiness 明细说明也必须使用专门文案，不能混写模型范围、成本倍率或调度优先级，避免管理员以为这把账号同时存在手工限制或策略覆盖。
- `allowed_models` 在未开启自动获取时，以及 `locked_models`、`model_include_patterns` 和 `model_exclude_patterns` 表示账号模型范围或过滤规则，迁移后应归入 `niffler_account_model_capabilities`，readiness 继续提示。
- `rate_multipliers` 和 `global_priority_by_format` 表示账号成本或调度覆盖，迁移后应归入 Niffler Core 上游账号成本倍率和调度策略，readiness 继续提示。
- readiness 只负责指出需要迁移或清理的旧范围/策略字段，不自动改写生产账号，也不删除协议和认证能力字段。

用户分组模型范围缺口判断规则：

- 旧用户分组的 `allowed_models_mode` 不是 `specific` 时，readiness 应标记为“模型范围未收敛”，不能简单写成“允许全部模型”。实际可用范围仍可能受可用 Provider、端点和账号能力限制；迁移前要确认的是产品策略是否需要明确可售模型列表。
- 旧用户分组的 `allowed_models_mode = specific` 但 `allowed_models` 为空时，readiness 应标记为“指定模型为空”，提示补齐可售模型或停用该分组后再迁移。

第 5 批第二片验证方式：

- 单元或路由测试覆盖冻结响应为 `409 Conflict`，响应体包含清楚的下一步页面提示，并带管理员审计事件。
- 编译验证覆盖 Niffler core 新增按账号 ID 查询方法的 PostgreSQL 实现。
- 前端类型检查和构建通过，确认对账页文案不再写“第一片只读、不冻结”。
- 生产验证只调用健康检查、readiness 和旧依赖稽核接口；不在生产执行批量写入测试，不在生产服务器编译。

第 5 批第三片运行时读源切换规则：

- 本片只切换已经打开 `niffler_runtime_rollout_settings.enable_new_routing` 的 API Key 或产品策略；没有打开新路由的请求继续走旧运行时读源。
- “已迁移运行时对象”的判定必须同时满足：用户 Key 存在 `niffler_api_key_product_plan_bindings` 绑定；绑定的 `niffler_product_plans` 存在且启用；API Key 或产品策略存在启用的运行时灰度配置，且 `enable_new_routing = true`。
- 已迁移对象的产品策略必须只读取 `niffler_product_plans` 和 `niffler_product_plan_models`：可用模型来自启用的产品策略模型；默认销售倍率来自产品策略；单模型销售倍率来自产品策略模型覆盖值，并在运行时转换成现有结算链路识别的 `global_model_id -> multiplier` 结构。
- 已迁移对象的上游供给必须只读取 `niffler_upstream_services`、`niffler_upstream_accounts` 和 `niffler_account_model_capabilities`：停用服务、停用账号、失效账号、额度耗尽账号、冷却中账号和未声明支持当前模型的账号不能进入调度。

- 已迁移对象缺少新配置时不能静默退回旧字段：没有产品策略绑定、产品策略停用、产品策略没有启用模型、请求模型不在产品策略内、没有可用上游服务、没有可用账号能力，都必须返回明确的平台配置错误或产品策略拒绝错误。
- 平台配置错误返回给用户时使用清楚文案，例如“平台暂时没有为该模型配置可用上游账号，请联系管理员处理”；模型不在产品策略内仍按用户无权使用该模型处理。
- 本片不重写传输层、不删除旧字段、不删除旧接口、不迁移生产数据、不批量更新账号状态；真正的旧接口只读投影放到第四片。
- 本片不在请求链路做无界查询：运行时最多按 API Key 读取一次灰度决策并缓存，按产品策略读取启用模型并限制条数，按请求模型读取启用账号能力并限制条数；超过限制时直接返回平台配置错误，避免部分读取导致错误调度。
- 运行时缓存失效必须覆盖产品策略绑定、产品策略模型、灰度配置和上游账号能力的后台写入；本片先使用短 TTL 缓存，后续再做精细化失效。

第 5 批第三片影响范围：

第 5 批第三片验证方式：

第 5 批第四片旧接口只读兼容规则：

- 已迁移对象的判定沿用第二片：旧 Provider ID 对应 `niffler_upstream_services.id`；旧 Provider Key ID 对应 `niffler_upstream_accounts.id`；旧 User Group ID 对应 `niffler_product_plans.id`；旧用户 Key ID 对应 `niffler_api_key_product_plan_bindings.api_key_id`。

- 已迁移 Provider Key 的旧读响应必须叠加 `niffler_upstream_accounts` 的账号名称、邮箱、手机号、状态、成本倍率、优先级和冷却时间；旧 Key 密钥内容、历史健康统计和 OAuth 快照只作为旧页面展示兼容，不再作为账号状态权威来源。
- 已迁移 Provider 模型价格旧读响应必须只读展示新账号模型能力或产品策略模型投影；本片不允许旧页面继续写 Provider 模型价格。旧模型价格表只作为未迁移 Provider 的读源。
- 已迁移用户分组的旧读响应必须以 `niffler_product_plans` 和 `niffler_product_plan_models` 为业务主数据：分组名显示产品策略名，可用模型和销售倍率来自新表；旧分组的允许 Provider、允许 API 格式和旧模型价格不再作为权威展示。
- 所有投影响应必须带只读标记：`niffler_core_projected: true`、`legacy_read_only: true`、`niffler_core_page: "/admin/niffler-core"`，并给出 `legacy_read_only_reason`，让旧前端能统一禁用写按钮并提示去 Niffler Core 修改。
- 未迁移对象继续返回旧读数据，但也必须保留旧写入口冻结逻辑；本片不批量迁移数据、不修改旧字段、不删除旧接口、不改变运行时调度、不改变计费、不改变结算和返利。
- 旧读投影不能做无界查询：列表分页沿用旧接口参数并限制上限；新表读取按当前页对象 ID 或固定分页读取，不能为了计算精确总数触发全表扫描。

第 5 批第五片稳定观察规则：

- 本片新增 `niffler_stability_observations`，每天自动记录一次稳定观察快照，不修改旧 Provider、旧 Key、旧分组、旧价格、旧调度、旧计费或旧返利。
- 观察窗口按 `window_start_unix_ms` 和 `window_end_unix_ms` 表示，固定为 UTC 自然日 24 小时窗口；同一天内后台重试或服务重启只更新同一条快照，不新增重复记录。
- 快照必须记录一致性看板问题数量、实际请求到上游但服务或账号仍无法确定的数量、旧写入口真实调用数量、异常预占数量、异常返利流水数量、回滚演练状态和阻断原因。
- 异常预占和异常返利流水必须按当前 UTC 自然日窗口统计，不能按全量历史统计。人工处理预占按进入 `manual_review` 的 `finalized_at_unix_ms` 计入窗口；超时仍未释放的 `active` 预占按 `expires_at_unix_ms` 计入窗口；返利失败按失败状态写入时的 `updated_at_unix_ms` 计入窗口。
- `unknown_upstream_count` 只统计 `request_candidates` 中已经开始尝试上游调用的记录，并且服务 ID 或账号 ID 为空、`unknown`、`unknow` 或 `pending`。平台内失败，例如用户 Key 并发上限、产品策略拒绝、没有可用上游账号，不能计入该指标。
- readiness 的 Key 残留项必须区分“手工限制”和“自动同步模型清单”。`auto_fetch_models = true` 时保存在旧 Key 上的 `allowed_models` 只能标记为“自动同步模型清单”，不能在页面上显示成“允许模型”或“限制”，避免管理员误判为手工白名单。
- 稳定观察状态只允许三类：`pass` 表示本窗口没有阻断项；`reset_required` 表示本窗口出现会让 T0 清零的阻断项；`pending` 表示数据不足或回滚演练状态未记录，不能计入稳定天数。
- 如果同一个窗口同时有 `reset_required` 类阻断和 `pending` 类阻断，状态按 `reset_required` 保存，`blocker_codes` 同时保留两类原因，避免管理员只看到一部分阻断项。
- 旧写入口真实调用读取管理员审计日志里的冻结尝试事件和旧入口成功写入事件。冻结尝试事件为 `niffler_legacy_write_frozen`；旧入口成功写入事件包括旧 Provider、旧 Provider Key、旧 Provider 端点、旧 Provider 模型价格、旧用户分组和旧用户 Key 限制相关写入。所有仍保留的旧写入口都必须挂审计事件，避免稳定观察漏算真实旧入口调用。如果某环境没有审计仓储，快照必须写明 `legacy_write_audit_unavailable`，状态为 `pending`，不能假装通过。
- 回滚演练状态通过专用记录接口写入，底层仍保存到系统配置；允许值为 `passed`、`failed`、`not_recorded`。记录 `passed` 时必须同时保存备份引用、可回滚镜像标签和演练说明；只有状态和值得追溯的证据同时存在，稳定观察才允许计入通过。
- 如果状态被通用系统配置手工改成 `passed`，但缺少回滚演练证据，快照必须写明 `rollback_drill_evidence_missing`，状态为 `pending`，不能假装通过。
- 后台任务必须限量查询，不做全表统计；每轮只生成一个固定窗口快照，同一窗口重复执行时更新同一条记录，保证任务可重试。
- 出现 P0/P1 计费或调度事故、金额误差、实际上游服务或账号 `unknown/pending`、旧写接口被真实调用、异常预占、异常返利流水或回滚演练失败，本窗口状态为 `reset_required`，T0 不能继续累计。
- 稳定观察只提供证据，不自动删除旧写逻辑、旧页面或旧字段读路径；第六片必须在 14 天快照全部满足稳定标准后才能执行。

第 5 批第五片接口：

- `GET /api/admin/niffler-core/stability-observations?offset=0&limit=50`
- `offset` 默认 0；`limit` 限制在 1 到 100。
- 返回最近稳定观察快照、状态、阻断原因和各项风险计数。
- 接口只读，不触发新快照生成，不修改任何业务数据。
- 后台页面至少读取最近 15 条稳定观察记录，用 UTC 自然日窗口连续性和 `pass` 状态计算稳定期进度。15 条用于同时覆盖当前未结束窗口和最近 14 个已结束窗口，避免当前窗口占掉一条记录后页面误判还差 1 天。页面只计算已经结束的观察窗口；最新窗口必须是当前 UTC 自然日窗口或刚结束的上一 UTC 自然日窗口。如果当前未结束窗口已经出现阻断项，也不能显示第六片可开始。已结束通过窗口少于 14 条、窗口不连续、最新窗口过期、任一已结束窗口不是 `pass`，都不能显示第六片可开始。
- `GET /api/admin/niffler-core/rollback-drill-evidence`
- `PUT /api/admin/niffler-core/rollback-drill-evidence`
- 专用回滚演练证据接口只写系统配置，不执行回滚、不执行数据库备份、不重启服务。`passed` 必须提交 `backup_reference`、`rollback_image_tag` 和 `drill_summary`，避免无证据标记通过。
- `not_recorded` 表示没有可用回滚演练证据，接口必须清空备份引用、可回滚镜像标签和演练说明，避免页面残留旧证据。

第 5 批第五片验证方式：

- 单元测试覆盖稳定观察快照判断：无阻断项且回滚演练证据完整为 `pass`，金额误差、`unknown`、旧写调用、异常预占、异常返利或回滚失败为 `reset_required`，审计不可用、回滚未记录或回滚证据缺失为 `pending`。
- 数据仓储测试覆盖快照写入幂等，同一窗口重复记录只保留一条。
- 路由测试覆盖稳定观察只读接口和回滚演练证据接口的管理路由分类和权限。
- 生产验证只调用健康检查、readiness、旧依赖稽核和稳定观察只读接口；不在生产执行批量写入，不在生产服务器编译。

## 需要持续验证的问题

- 旧 `api_keys.allowed_providers`、`allowed_models`、`allowed_api_formats` 是否还有真实业务依赖。
- 旧分组里允许的模型、允许的端点、允许的提供商和提供商模型价格之间是否存在冲突。
- 现有请求记录中 `unknown` 的具体来源。
- 停用 Provider 是否仍被旧分组配置引用。
- API Key 是否存在缺失分组、分组改名导致引用断裂、或产品策略缺失的问题。
- 第三方 OpenAI 兼容接口是否只支持图片接口，还是也支持 Responses 对话内图片工具。
- 哪些高成本请求需要启用预占，以及预占上限如何按模型和请求类型计算。
- 钱包页、使用记录、资金流水和日汇总是否仍有“用量金额”和“真实钱包扣款”混用。
- 邀请返利是否存在支付成功但未发放、重复发放或无法解释未发放原因的订单。
- 本地和 CI 是否存在会长期占满磁盘的构建缓存、镜像包或临时产物。
